Java Language

    Module Import Declarations
          Module Import Declarations was introduced in JDK 23 as a preview
          feature (JEP 476), and previewed again in JDK 24 (JEP 494), then
          became a standard feature in JDK 25 (JEP 511).


    Import declarations are basic constructs in Java programming language. In a
    Java source file, to use an other class, this class must be imported first, unless
    that class is in the same package, or it’s in the java.lang package.

    Before Java 23, there were four types of import declarations. These import
    declarations are actually divided into two categories:


       • A single-type-import declaration imports a single class or interface by giv-
         ing its canonical name. For example, import java.util.List imports
         the interface java.util.List.
       • A type-import-on-demand declaration allows all accessible classes and
         interfaces of a named package, class, or interface to be imported as
         needed. For example, after using import java.util.*, all accessible
         classes and interfaces of java.util package will be imported as needed.


    Below is the grammar of import declarations before Java 23.

    Figure 7. Import declarations before Java 23

1   ImportDeclaration:
2     SingleTypeImportDeclaration
3     TypeImportOnDemandDeclaration
4     SingleStaticImportDeclaration
5     StaticImportOnDemandDeclaration




    Module Import Declaration

    In Java 23, a new module import declaration is added. As shown in the code
    below, M is the module to import.
    Module Import Declarations                                                8


    Figure 8. Module import declaration

1   import module M;



    This declaration imports, on demand, all of the public top-level classes and
    interfaces in


       • The packages exported by the module M to the current module, and
       • The packages exported by the modules that are read by the current
         module due to reading the module M.


    Below is the new grammar of import declarations from Java 23. ModuleIm-
    portDeclaration is newly added.

    Figure 9. Import declarations from Java 23

1   ImportDeclaration:
2     SingleTypeImportDeclaration
3     TypeImportOnDemandDeclaration
4     SingleStaticImportDeclaration
5     StaticImportOnDemandDeclaration
6     ModuleImportDeclaration
7
8   ModuleImportDeclaration:
9     import module ModuleName;




    Import Ambiguity

    Importing a module has the effect of importing multiple packages. In these
    imported packages, there may be multiple classes with the same simple name.
    Using this kind of simple names will cause a compile-time error due to
    ambiguous imports.

    For example, modules java.base and java.sql both export a Date class,
    java.util.Date and java.sql.Date.

    In the code below, after importing java.base and java.sql, we cannot use
    Date directly, because the name of Date is ambiguous.
    Module Import Declarations                                                    9


    Figure 10. Ambiguous Date

1   import module java.base;
2   import module java.sql;
3
4   Date d = ...



    To resolve ambiguities, we can add another import declaration to specify the
    correct type to use.

    In the code below, after adding import java.sql.Date, the ambiguity is
    resolved.

    Figure 11. Resolve ambiguity

1   import module java.base;
2   import module java.sql;
3
4   import java.sql.Date;
5
6   Date d = ...



    These three import declarations have their specificity. Below is the list of
    import declarations from most specific to least specific.


      1. single-type-import declaration,
      2. type-import-on-demand declaration,
      3. module import declaration.


    An import declaration can shadow import declaration that are less specific.


       • A single-type-import declaration can shadow both a type-import-on-
         demand declaration and a module import declaration.
       • A type-import-on-demand declaration can shadow a module import dec-
         laration.


    In a source file, we can organize import declarations by their specificity, from
    least specific to most specific.
     Module Import Declarations                                                  10


     Figure 12. Organize import declarations

1    // Module imports
2    import module java.base;
3    import module java.sql;
4
5    // Package imports
6    import java.util.*;
7
8    // Single-type imports
9    import java.sql.Date;




     Choose Import Declaration

     Given a type, it can be imported by using one of these three import dec-
     larations. For example, for the type java.util.List, it can be imported
     using import java.util.List, import java.util.*, and import module
     java.se. For these three import declarations, it’s usually recommended to
     prefer single-type-import declarations.

     There are some scenarios where module import declarations are useful. For
     a Java source file, only the package java.lang is imported on demand. For
     most Java programs, there are some commonly used classes and interfaces, like
     java.util, java.io, and java.time. Using single-type-import declarations
     to import all these common types is a tedious task.

     The code below shows a simple program to count names by their first charac-
     ter. In this program, we need to import types from java.util package.



     Figure 13. Simple program using Stream

1    import java.util.Map.Entry;
2    import java.util.stream.Collectors;
3    import java.util.stream.Stream;
4
5    public class NameCounter {
6
7      void count() {
8        var result = Stream.of("Alice", "Alex", "Amelia", "Andrew",
9                "Bob", "Bella", "Brian", "Bianca", "Ethan", "Emma")
10           .collect(
11               Collectors.groupingBy(name -> name.toUpperCase().substring(0, 1),
     Module Import Declarations                                                11


12                       Collectors.counting()))
13               .entrySet()
14               .stream()
15               .sorted(Entry.comparingByValue())
16               .toList();
17           System.out.println(result);
18       }
19
20       static void main() {
21         new NameCounter().count();
22       }
23   }



     By using a module import declaration, these three import declarations can be
     simplified to a single import module java.se.
Flexible Constructor Bodies
     Flexible Constructor Bodies was introduced in JDK 22 as a preview
     feature (JEP 447), then previewed again in JDK 23 (JEP 482) and JDK
     24 (JEP 492), and finally became a standard feature in JDK 25 (JEP
     513).


When learning Java, we all remember a Java syntax rule related to class
inheritance and constructors. When inheriting from a class, the subclass’s
constructor must use super to call the superclass’s constructor. This super
statement must be the first statement in the constructor method. If super
is not the first statement, a compilation error occurs. This rule also applies
to calling the constructor of the same class, that is, when calling this. this
statement in the constructor must also be the first statement.

When a class inherits from another class, the subclass inherits functionality
from the superclass and adds its own fields and methods. The initial values of
the subclass’s fields may depend on the initial values of the superclass’s fields.
Therefore, the superclass’s fields must be initialized before the subclass’s fields.

To ensure the order of field initialization, constructors must be run in a top-
down manner. The superclass’s constructor must run before the subclass’s
constructor. Another restriction is that the class’s fields cannot be accessed
before they are initialized. To ensure this, code in constructors cannot access
fields in the current class, and accessing fields in superclasses must wait until
the superclass’s constructor completes.

To ensure that superclass fields are initialized first, Java 1.0 has adopted a
very strict syntax, requiring super and this to be the first statement in a
constructor. This restriction prevents access errors, but it also limits many
legitimate use cases.

This restriction was removed in Java 22. In constructor methods, super and
this statements are no longer required to be the first statement. Other
statements can precede them. Of course, the top-down execution requirement
of constructors remains unchanged, and fields cannot be accessed before
initialization. These two restrictions still apply.
     Flexible Constructor Bodies                                                 13


     If other statements precede super and this, the compiler will perform stricter
     checks to ensure that these statements do not violate these restrictions. Java
     developers do not need to pay too much attention to the syntax rules; if there
     are any problems, the compiler will report an error, then you can then fix them
     accordingly.

     Allowing statements before super simplifies three scenarios related to con-
     structor parameters in constructor implementation.

     The first is constructor parameter validation. If the subclass constructor’s
     parameters fail validation, an exception can be thrown directly without calling
     the superclass constructor.

     In the code below, the subclass Child1 validates the value of its constructor
     parameter value before calling the superclass constructor.



     Figure 14. Constructor parameter validation

1    /**
2     * Validating superclass constructor arguments
3     */
4    class Super1 {
5
6        private int value;
7
8        Super1(int value) {
9          this.value = value;
10       }
11   }
12
13   public class Child1 extends Super1 {
14
15       Child1(int value) {
16         if (value < 0) {
17           throw new IllegalArgumentException("invalid value");
18         }
19         super(value);
20       }
21   }



     The second is constructor parameter preparation. This often occurs when
     the superclass constructor’s parameters differ significantly from the subclass
     constructor’s. The subclass constructor method must execute complex logic
     to obtain the parameters passed to the superclass constructor. This logic can
     Flexible Constructor Bodies                                                  14


     be placed before the super call, making the constructor code clearer and easier
     to understand.

     In the code below, the subclass Child2 calculates the newId based on the
     value of its constructor parameter, then the newId is used to call superclass
     constructor.



     Figure 15. Constructor parameter preparation

1    import java.util.UUID;
2
3    /**
4     * Preparing superclass constructor arguments
5     */
6    class Super2 {
7
8        private String id;
9
10       Super2(String id) {
11         this.id = id;
12       }
13   }
14
15   public class Child2 extends Super2 {
16
17       Child2(String oldId) {
18         String newId;
19         if (oldId != null) {
20           newId = "o_" + oldId.toLowerCase();
21         } else {
22           newId = UUID.randomUUID().toString();
23         }
24         super(newId);
25       }
26   }



     The third type is shared constructor parameters. The parent class’s con-
     structor may have multiple parameters of the same type, and the child class’s
     constructor uses the same value as the values of multiple parameters in the
     parent class’s constructor.

     In the code below, the constructor of superclass Super3 requires two int pa-
     rameters. One constructor of subclass Child3 accepts a single int parameter.
     The two parameters of the superclass constructor share the same value, and
     its value only needs to be calculated once.
     Flexible Constructor Bodies                   15




     Figure 16. Shared constructor parameters

1    /**
2     * Sharing superclass constructor arguments
3     */
4    class Super3 {
5
6        private int v1;
7        private int v2;
8
9        Super3(int v1, int v2) {
10         this.v1 = v1;
11         this.v2 = v2;
12       }
13   }

    Instance main methods

    Before Java 21, the entry point of launching a Java program must be a public
    static void main(String[] args) method. Starting from Java 21, the
    launching protocol of a Java application has changed. The Java launcher is now
    flexible about choosing the main method.

       • If the class declares or inherits a main method with a String[] parameter
         then the launcher chooses that method. Otherwise, if the class declares
         or inherits a main method with no parameters then the launcher chooses
         that method. Otherwise, the launcher reports an error and terminates.
       • If the chosen method is static then the launcher invokes it. Otherwise,
         the class must have a non-private constructor with no parameters. The
         launcher invokes that constructor and then invokes the chosen main
         method of the resulting object. If there is no such constructor then the
         launcher reports an error and terminates.

to the target type without loss of information. For example, a conversation
from long to int may be exact depends on the runtime.

Stream Gatherers
     Stream Gatherers was introduced in JDK 22 (JEP 461) as a preview
     feature, then previewed again in JDK 23 (JEP 473), and became a
     standard feature in JDK 24 (JEP 485).


Since Java 8 introduced stream, it has been used very frequently in Java
applications.

The pipeline for stream processing consists of three parts:


   • a source,
   • intermediate operations,
   • a terminal operation.


The source is the source of elements in the stream and can be created using
the Stream.of method or obtained from a collection. Intermediate operations
process the elements in the stream and are defined in the Stream interface.
These include map, filter, flatMap, and distinct. Terminal operations,
which ultimately produce a result or side effect, include collect, reduce,
count, and forEach.

A major pain point when using streams is that intermediate operations cannot
be customized. We can only use those provided by the Stream interface.
Stream in the standard library cannot be modified to add more intermediate
operations. This can make using streams awkward in some cases. For example,
Stream includes the intermediate distinct operation, which can remove
duplicate elements from the stream, but it only removes duplicates based
on object equality. In real-world development, a common requirement is to
remove duplicates based on object properties. For example, given a stream
contains Student objects representing students, we may want to remove
duplicates based on the id property of these Student objects. This cannot
be achieved with built-in distinct.

Java 22 introduced the Gatherer interface, which allows application code to
provide custom intermediate stream operations.
     Stream Gatherers                                                            33


     A Gatherer interface consists of four methods: initializer, integrator,
     combiner, and finisher. Only the integrator is required; the others are
     optional.

         • The initializer creates new mutable state; it’s not required for state-
           less gatherers.
         • The integrator provides elements to be passed downstream.
         • The combiner is used for parallel processing to merge intermediate state;
           it’s not required for sequential processing.
         • The finisher performs additional processing on the final result.

     Gatherers are created using the of method on Gatherers and used by the
     gather method on streams.

     The following code demonstrates how to use a Gatherer to implement dis-
     tinct operations based on object properties. This Gatherer implementation
     uses sequential processing, so a combiner is not required. State represents
     the intermediate state, with a Map used to record previously encountered
     values. The initializer returns a new State object. The integrator calls
     the provided extractor function for each element, extracting property values
     from the element object. The property values serve as the keys to the Map, and
     the values are the elements themselves. The finisher examines all values in
     the Map in State and adds these value objects to the downstream using the
     push method. This is the value passed to the downstream.



     Figure 42. distinct by object properties

1    /**
2     * Distinct by an object's property, keep last duplicated element
3     */
4    public class DistinctBy {
5
6      /**
7       * Create a new {@linkplain DistinctBy} gatherer
8       *
9       * @param extractor Extract the property from an element
10      * @param <T>       Type of the element
11      * @param <R>       Type of the element's property
12      * @return A new {@linkplain DistinctBy} gatherer
13      */
14     static <T, R> Gatherer<T, ?, T> of(
15         Function<? super T, ? extends R> extractor) {
     Stream Gatherers                                                                   34


16           class State {
17
18               final Map<R, T> seen = new HashMap<>();
19           }
20
21           return Gatherer.ofSequential(State::new, Integrator.ofGreedy(
22                   ((state, element, _) -> {
23                     state.seen.put(extractor.apply(element), element);
24                     return true;
25                   })),
26               (state, downstream) -> state.seen.values().forEach(downstream::push)
27           );
28       }
29   }

Class‐File API
     Class-File API was introduced in JDK 22 (JEP 457) as a preview feature,
     and it’s previewed again in JDK 23 (JEP 466), then became a standard
     feature in JDK 24 (JEP 484).


Class-File API is the standard API for parsing, generating, and transforming Java
class files. The Class-File API resides in the java.lang.classfile package
and sub-packages.


ClassFile

java.lang.classfile.ClassFile is the entry point of using Class-File API.
A ClassFile serves as a context that defines the options governing the
processes of parsing and generation. A ClassFile is created using the static
of() method. The of() method accepts a list of Options. If no Options are
provided, ClassFile use a list of default options.

After creating a ClassFile, it can be used to parse, generate, and transform
class files.


   • parse method parses a file or a byte array and gets a ClassModel
     representing the parsed class file.
   • build method builds a class file into a byte array using a ClassBuilder.

Integrity by Default
Prepare to Restrict the Use of JNI

     Prepare to Restrict the Use of JNI was introduced in JDK 24 (JEP 472).

In current Java versions, if you need to interact with native code, you have two
options. The first is the JNI, which has been available since JDK 1.1. The other
is the Foreign Function & Memory API, the FFM API, which became officially
available in JDK 22. For most applications, the JNI remains the most common
choice.

Using the JNI and FFM to interact with native code is highly dangerous.
Improper use can directly cause the JVM to crash.

To ensure the integrity of the Java platform, code that loads and links native
libraries is restricted. In JDK 24, calling code that loads and links native libraries
will generate a warning on the first call. This applies to both JNI and FFM. In
future Java versions, this warning will be upgraded to an exception.

The following methods that access native code are restricted:

   • The load and loadLibrary methods of the System class.
   • The load and loadLibrary methods of the Runtime class.

Methods declared as native are bound to methods in the native library on first
call. This binding is also restricted.

To avoid warnings and future exceptions, we can enable native access using
the command-line option --enable-native-access. The value of this option
is a comma-separated list of module names, or ALL-UNNAMED for all unnamed
modules. No warnings or exceptions are output for modules that are allowed
to access native code.

If code in a module is not allowed to access native code, the Java runtime
can take different actions when code in that module attempts to access native
code. The specific actions are configured with the option --illegal-native-
access. This option has three possible values.
Integrity by Default                                                           46


    • allow allows these access actions.
    • warn allows these access actions but outputs a warning. This is the default
      value in JDK 24.
    • deny throws an IllegalCallerException for each access action. This
      will become the default in future Java versions.


If you encounter warning messages when using JNI, follow the instructions to
add the --enable-native-access option.



Warn upon Use of Memory‐Access Methods in
sun.misc.Unsafe

Unsafe in Java is a special class.     It provides many features for efficient
memory operations. Unsafe was introduced to Java in 2002. Its package name,
sun.misc, indicates that it is an internal class of the JDK, intended for use only
by JDK internal code and not for external applications. However, previous Java
versions did not provide a way to restrict application access to internal classes.
The features provided by Unsafe are extremely useful and are used by many
performance-critical applications, including Apache Hadoop and Cassandra.
However, as the name suggests, the methods in Unsafe are unsafe. Improper
use can at best degrade application performance or even cause the JVM to
crash. Unsafe is a powerful double-edged sword.

One of the development directions of Java is to ensure system integrity. A key
part of this is restricting access to JDK internal classes. When JDK 9 introduced
the module system, most JDK internal classes were encapsulated, but Unsafe
was an exception due to its widespread use. Restricting Unsafe would cause
problems in many applications. Therefore, the restrictions on Unsafe were
delayed for a long time. It wasn’t until JDK 23 that the methods in Unsafe were
declared deprecated.

In Java 24, a warning message is output by default when a memory access
method in Unsafe is used for the first time. JDK 23 added the startup parameter
--sun-misc-unsafe-memory-access, which has four possible values: allow,
warn, debug, and deny.


    • In JDK 23, the default value is allow, which allows the use of these
      memory access methods.
Integrity by Default                                                          47


    • In JDK 24, the default value is warn, which outputs a warning message
      when these methods are used.
    • debug outputs a warning and a stack trace every time an Unsafe memory
      access method is used.
    • If the parameter value is deny, any use of these memory access methods
      will directly throw an UnsupportedOperationException.


In JDK 26, deny becomes the default value for this parameter. In subsequent
versions, these memory access methods will be removed.

Most applications don’t use Unsafe directly. The JDK already provides standard
alternatives to Unsafe.


    • For heap memory operations, we can use VarHandle introduced in Java
      9.
    • For off-heap memory operations, we can use Foreign Function & Memory
      API, which became official in Java 22.


If Unsafe is still used in your code, you should replace it with the standard API
as soon as possible.
Security
Permanently Disable the Security Manager

     Permanently Disable the Security Manager was introduced in JDK 24
     (JEP 486).


Security is an important aspect of application development. When you think
of security features in Java, there are many third-party libraries that come to
mind. In fact, the Java Standard Library has a Security Manager since 1.0, to
restrict Java applications’ access to system resources, including the file system
and network, and to perform sensitive operations.

Despite its early introduction, Security Manager is rarely used by external
applications. Security Manager is disabled by default and is rarely enabled.

Security Manager is deprecated in Java 17. In Java 24, Security Manager is
permanently disabled.

Starting with Java 24, you cannot use the system property, -
Djava.security.manager to enable Security Manager. At runtime, you
cannot install the SecurityManager using the System’s setSecurityManager
method. The APIs associated with the Security Manager, while still preserved,
are rendered as non-functional. These APIs are retained for backward
compatibility. Some constructors and methods in the Java standard library,
may throw SecurityExceptions at runtime. After Security Manager is
disabled, SecurityExceptions are no longer thrown, so the documentation
for these apis, has been updated to remove SecurityException.

Because Security Manager is rarely used, disabling it will not affect the vast
majority of existing applications. The only thing that might be affected is the
use of Security Manager to block calls to some Java platform APIs, especially
the System.exit method. When Security Manager is disabled, the Java stan-
dard library does not provide an alternative solution, but requires application
developers to switch to other methods, such as transforming Java bytecode at
runtime.
Security                                                                    49


It is a good thing that the Security Manager is disabled. With Security Manager
disabled, code in the Java standard library no longer requires permission
checks, greatly reducing maintenance costs. Java development team can focus
on more important security features.

Scoped Values
     Scoped Values was introduced in JDK 20 as an incubating feature (JEP
     429), and became a preview in JDK 21 (JEP 446), then previewed again
     in JDK 22 (JEP 464), JDK 23 (JEP 481), and JDK 24 (JEP 487), and became
     a standard feature in JDK 25 (JEP 506).

To invoke a method, we need to pass parameters to it. Sometimes it’s not easy
to pass parameters down the call stack. For example, method A calls method B,
then method B calls method C. Suppose that method C requires a parameter a,
this parameter needs to be passed from method A. Even though this parameter
a is not used in method B, this parameter still needs to be declared in method
B, and then passed to method C.

This approach doesn’t scale for deep call stacks. We may need to modify
signatures of many methods to pass parameters down the call stack. What we
need is a convenient way to share values across different methods, like implicit
parameters that can be used between methods.
A typical example is security context object used in Spring Security. This
context object is populated after the user has successfully authenticated. This
context object contains basic information about current user. This context
object may be used in different places of the code, so it not feasible to required
this object to be passed in as a method parameter.


Thread Local

Thread-local variables are used to share data between methods on the call
stack without using method arguments. A thread-local variable is a variable of
type java.lang.ThreadLocal. A thread-local variable has one current value
per thread. Code running in one thread automatically reads and writes the
value associated with the current thread.
In Spring Security, ThreadLocalSecurityContextHolderStrategy is the
strategy to hold SecurityContext objects using thread-local variables. As
shown in the code below, the ThreadLocal object contextHolder holds the
SecurityContext object.
    Scoped Values                                                                      52


    Figure 53. Use a thread-local variable

1   private static final ThreadLocal<Supplier<SecurityContext>> contextHolder =
2       new ThreadLocal<>();



    Thread-local variables have some problems.

        • Unconstrained mutability - All thread-local variables are mutable. Any
          code that has access to a ThreadLocal object can use the set() method
          to update its value. When the ThreadLocal object is modified in different
          places, it’s hard to track the current value that held by this object.
        • Unbounded lifetime - Once a value is set to a ThreadLocal object for the
          current thread, this value is retained for the life-time of the thread, or until
          code running in the thread calls the remove() method. Unfortunately,
          developers rarely call remove() method to clear the reference, so per-
          thread data is often retained for a longer time than necessary.
        • Expensive inheritance - Thread-local variables of a parent thread can
          be inherited by child threads. For inheritable thread-local variables,
          child threads need to allocate storage for those variables. This can add
          significant memory footprint.

    Virtual threads are instances of java.lang.Thread, and can have thread-local
    variables. However, virtual threads are light-weight and short-lived. There
    may be millions of virtual threads, then the memory pressure will be too high
    with inheritable thread-local variables.

Structured Concurrency
     Structured Concurrency was introduced in JDK 19 (JEP 428) as an
     incubating API, and incubated again in JDK 20 (JEP 437), and became
     a preview feature in JDK 21 (JEP 453), then preview again in JDK 22
     (JEP 462), JDK 23 (JEP 480), JDK 24 (JEP 499), and JDK 25 (JEP 505).


Structured concurrency is a coined term. It’s described in details in this post.
The key point of structured concurrency is structured. Structured means the
structure of concurrent tasks should match the code structure. By leveraging
structured concurrency, developers can write concurrent programs just like
single-threaded programs. All the heavy-lifting jobs are done by the underlying
framework.


     Kotlin Coroutines is a great example of using structured concur-
     rency. New coroutines can be only launched in a specific Corou-
     tineScope which delimits the lifetime of the coroutine.


Considering that we are creating an API to expose a user’s information in
an e-commerce application. When using microservice architecture, a user’s
information may be maintained by different services. We may need to fetch
data from multiple sources and assemble them to get the final result.

The code below shows a simple getUser() method to load and assemble a
user’s information. It fetches data from three different sources. We can treat
the getUser() method as a task, while those three methods fetchUserBa-
sicInfo(), fetchFavoriteStores() and fetchOrders() are subtasks of the
main task.
    Structured Concurrency                                                         58


    Figure 60. A scenario of data loading

1   public UserData getUser(String userId) {
2     UserBasicInfo basicInfo = fetchUserBasicInfo(userId);
3     List<Store> favoriteStores = fetchFavoriteStores(userId);
4     List<Order> orders = fetchOrders(userId);
5     return assemble(basicInfo, favoriteStores, orders);
6   }



    Apparently, there is a dependency between the main task and subtasks.


       • The main task can only complete when all the subtasks complete.
       • If any of the subtask failed, the main task will also fail. All other ongoing
         subtasks should be cancelled, because there results won’t be used any
         more.


    If all subtasks are executed synchronously in a single thread, then we can easily
    get the following assumptions:


       • If fetchUserBasicInfo() method fails, both fetchFavoriteStores()
         and fetchOrders() methods won’t be executed, getUser() method
         returns immediately.
       • getUser() method completes after assemble() completes, fetchUser-
         BasicInfo(), fetchFavoriteStores() and fetchOrders() methods
         all complete successfully before that.


    These assumptions can be easily derived from the code structure of getUser()
    method. Those three methods are contained in the block of getUser()
    method, so their life time is confined by the outer method.

    If subtasks are executed asynchronously in different threads, then we cannot
    make the same assumption.


       • Even getUser() method returns due to a failure in a subtask, all other
         subtasks may still be running in their own threads.
       • If fetchUserBasicInfo() method fails, other two subtasks may still run
         to their ends.
Structured Concurrency                                                       59


It’s possible to implement getUser() method correctly with multi-threading
support in Java, including Executors and thread pools. However, it’s not an
easy task, even for most-experienced developers. You have to deal with Ex-
ecutors, thread pools, thread interruption, timeout, cooperative cancellation,
graceful shutdown, and other issues.

With structured concurrency, we can simply treat concurrent subtasks as they
are running in a single thread. Those assumptions for synchronous execution
still hold. This makes concurrent programming much easier.



Basic Usage

The main API to use structured concurrency is java.util.concurrent.StructuredTaskSc
A StructuredTaskScope object is a scope where subtasks are executed in.
StructuredTaskScope<T, R> is a generic type.


   • T: the result type of subtasks executed in the scope.
   • R: the result type of the scope.


The workflow of using StructuredTaskScope is as follows:


  1. The main task creates a StructuredTaskScope object using Struc-
     turedTaskScope.open.
  2. Use the fork() method to create a new subtask.
  3. Calls the join() method to wait for subtasks to complete or be cancelled.
  4. After joining, handle any errors in the subtasks and process their results.
  5. Close the scope, usually implicitly via try-with-resources.

Synchronize Virtual Threads without
Pinning
     Synchronize Virtual Threads without Pinning was introduced in JDK
     24 (JEP 491).

Threads in Java are divided into platform threads and virtual threads. Platform
threads are heavyweight, corresponding one-to-one with native threads in the
operating system and scheduled by the operating system. An application is
limited in the number of platform threads it can create. Virtual threads are
lightweight and are created and scheduled by the Java runtime. Virtual threads
consume very few resources, and the theoretical number of virtual threads that
can be created is limited only by the system’s memory capacity. On a typical
machine, creating millions of virtual threads is not a problem.

At runtime, a virtual thread is assigned to a plat form thread by the JDK
scheduler. This process is called mounting the virtual thread to a platform
thread. This mounted platform thread is called the carrier of virtual thread.
After being mounted to a platform thread, a virtual thread runs the virtual
thread’s code. If the code execution is blocked for some reason, the virtual
thread is unmounted from the current platform thread, and the scheduler
mounts another virtual thread to the current platform thread. During the
execution of an application, a virtual thread may be scheduled to run on
different platform threads, and a platform thread may run the code of multiple
virtual threads. The mounting and unmounting of virtual threads is frequent
and transparent.

The mounting relationship between virtual threads and platform threads
demonstrates that to improve application performance, it’s necessary to
ensure that virtual threads can be properly unmounted from platform threads.
In some cases, a virtual thread cannot be unmounted from a platform thread,
causing it to be pinned on the platform thread. When a virtual thread is
pinned, its carrier cannot run other virtual threads.

In Java 21 through 23, virtual threads can be pinned for two reasons: when
executing a synchronized method or code block, and when executing a native
Synchronize Virtual Threads without Pinning                                    70


or foreign method. The impact of being pinned while executing a native or
foreign method is minimal, as most Java applications rarely use native or foreign
methods. However, the first scenario, when executing a synchronized method
or code block, is very common in application code and occurs extensively in
multi-threaded code.

Prior to Java 24, synchronized methods or code blocks could be pinned due
to the Java synchronized implementation. This implementation relies on a
monitor on each object. A monitor on an object can only be acquired by one
thread at most. When running synchronized code, it first acquires the monitor
on the current object and then releases the monitor after execution completes.

In its implementation, the JVM keeps track of the thread currently holding an
object’s monitor, but this relationship is of the platform thread, not the virtual
thread. Imagine an object obj whose class declares synchronized methods.
If virtual thread A is allowed to unmount while executing a synchronized
method on object obj, then after virtual thread A unmounts, a new virtual
thread B might be scheduled onto the same platform thread to execute another
synchronized method on object obj. When virtual thread B is scheduled to
execute, since it is on the same platform thread, the JVM will assume that
virtual thread B already holds the monitor on object obj and allow virtual thread
B to execute other synchronized methods. This violates the mutual exclusivity
between virtual threads A and B, causing thread synchronization issues.

Because synchronized locks can cause virtual threads to lock, affecting ap-
plication performance, prior to Java 24, the common practice was to replace
synchronized with locks in the java.util.concurrent package. However,
this requires code modifications.

Java 24 modified the JVM’s internal implementation of the synchronized
keyword. Virtual threads can acquire, hold, and release object monitors
independently of the platform thread to which they are currently mounted.
When a virtual thread’s code blocks acquiring an object monitor, the virtual
thread is unmounted from its carrier. The JDK scheduler can then schedule
other virtual threads onto the platform thread. Once the monitor is released,
other virtual threads waiting on the monitor can be rescheduled. Only virtual
threads that have acquired a monitor can run synchronized methods.

When a virtual thread is pinned, the JFR event jdk.VirtualThreadPinned is
logged. Since the synchronized keyword no longer causes a virtual thread to
be pinned, this event is only generated by calls to native or foreign methods.
Synchronize Virtual Threads without Pinning                                  71


The event itself has also been updated to include the reason the virtual thread
was pinned and the identifier of the carrier platform thread. The system
property jdk.tracePinnedThreads prints a stack trace of the current thread
when a virtual thread is pinned while running a synchronized method. Java
24 removed this system property.

Because the synchronized keyword no longer causes virtual threads to be
pinned, existing code using synchronized no longer needs to be modified.
This removes a major obstacle to the adoption of virtual threads.
Stable Values
     Stable Values was introduced in Java 25 as a preview feature (JEP 502).


Stable values are objects that hold immutable data. When writing Java pro-
grams, it’s recommended to use immutable objects. If an object is immutable,
once the object is initialized, its state won’t change. So an immutable object
can be shared freely across multiple threads.

An immutable object cannot be updated after initialized. Ideally, an immutable
object should only be initialized when necessary.

The Java Platform’s main tool for managing immutability is final fields. final
fields have restrictions. They must be set eagerly, either during construction
for instance fields or during class initialization for static fields. The order in
which final fields are initialized is determined by the textual order in which
the fields are declared.

final fields must be initialized eagerly. Objects referenced by final fields
may be expensive to create, which will slow down the start of the application.
Not all these final fields will actually be used in the runtime, which means
some eager initializations are unnecessary.

To avoid unnecessary initialization, we can use mutable non-final fields. But
this means we need to use code to ensure the correctness of immutability. This
is not an easy task.

A stable value is an object, of type StableValue, that holds a single data value,
its content. A stable value must be initialized some time before its content is
first retrieved, and it is immutable thereafter. A stable value is a way to achieve
deferred immutability.

    Constant Folding Optimization

    Constant folding is an optimization to evaluate constant expressions at compile
    time or JIT time instead of runtime. For the Java compiler, it will replace
    expressions made up entirely of compile-time constants with their evaluated
    value.

    In the code below, the final field secondsIn30Days has value 2592000 in the
    compiled class file.

    Figure 81. Constant folding in Java compiler

1   final int secondsIn30Days = 30 * 24 * 60 * 60; // folded to 2592000



    Some expressions cannot be resolved at compile time as constants, but they are
    actually constants and JVM can perform constant folding on them to improve
    performance. This is true for those lazily initialized immutable fields. Even
    though this kind of fields are non-final, the JVM can trust that their values
    will not change after their initial and only update.

    JVM can perform constant folding optimization on stable values. This is done
    by using JDK internal @jdk.internal.vm.annotation.Stable annotation. If

Garbage Collectors
There are changes related to built-in garbage collectors, including G1, ZGC,
and Shenandoah.



G1

Region Pinning

     Region Pinning for G1 was introduced in JDK 22 (JEP 423).


JNI defines functions to get and release direct pointers to Java objects. These
functions must always be used in pairs. Code within such function pairs is
considered to run a critical region. The Java object available for use during
that time is a critical object.

When a Java thread is in a critical region, G1 simply disables GC. This has a
significant impact on latency.

With region pinning in for G1, only the regions that contain critical objects will
be pinned. Garbage collection is still done in unpinned regions.

Generational Mode by Default

     ZGC: Generational Mode by Default was introduced in JDK 23 (JEP
     474).


Generational ZGC was made the default mode of ZGC. The command-line
option ZGenerational has a default value of true.

Compact Object Headers
     Compact Object Headers was an experimental feature in JDK 24 (JEP
     450) and became a production feature in JDK 25 (JEP 519).


With compact object headers, the size of object headers in the HotSpot JVM is
reduced from between 96 and 128 bits down to 64 bits on 64-bit architectures.

Before using compact object headers, the object header layout is split into a
mark word and a class word.


   • The mark word comes first, has the size of a machine address.
   • The class word comes after the mark word. It takes one of two shapes,
     depending on whether compressed class pointers are enabled. Uncom-
     pressed class pointers have a size of 64 bits, while compressed class
     pointers have a size of 32 bits.


On 64-bit architectures, if compressed class pointers are enabled, the size of
object header is 64 + 32 = 96 bits. If compressed class pointers are disabled,
the size of object header is 64 + 64 = 128 bits.

Compressed class pointers are enabled by default, but can be disabled via XX:-
UseCompressedClassPointers. The only reason to disable them, however,
would be for an application that loads more than about four million classes.

For compact object headers, the original mark word and class word are
combined into a 64 bits structure. Compressed class pointers are required
to be enabled and, moreover, the size of compressed class pointers is reduced
from 32 bits to 22 bits by changing the compressed class pointer encoding.

There are various experiments that demonstrate the performance improve-
ments by enabling compact object headers. These experiments show less heap
use, less CPU time, and less number of garbage collections. But you should still
run your own tests to verify the results of enabling it.

Compact object headers can be enabled with -XX:+UseCompactObjectHeaders.

    Class Loading & Linking

    JVM supports an ahead-of-time cache which can store classes after reading,
    parsing, loading, and linking them. Once a cache is created for a specific
    application, it can be re-used in subsequent runs of that application to improve
    startup time.


    Create a Cache

    To create a cache, we first need to run the application once to record its AOT
    configuration. This is called a training run. The AOT configuration is saved to
    a file.

    In the command below, -XX:AOTMode is set to record, and the AOT configu-
    ration is saved to the file app.aotconf.

    Figure 90. Create AOT configuration

1   java -XX:AOTMode=record -XX:AOTConfiguration=app.aotconf \
2       -cp app.jar com.example.App



    After the configuration file is created, the cache can be created using the
    command below.


       • -XX:AOTMode is set to create.
       • -XX:AOTConfiguration is set to the configuration file created in the first
         command.
       • -XX:AOTCache is the cache file.
    Project Leyden                                                             89


    Figure 91. Create a cache

1   java -XX:AOTMode=create -XX:AOTConfiguration=app.aotconf \
2       -XX:AOTCache=app.aot -cp app.jar



    This cache file can be used when running the application.

    Figure 92. Start application using a cache

1   java -XX:AOTCache=app.aot -cp app.jar com.example.App



    If the cache file is unusable or does not exist, then the JVM issues a warning
    message and continues.

    This two-step flow to create a cache can be simplified with the option AOT-
    CacheOutput, which specifies an AOT cache output file. When this option
    is used alone, with no other AOT options, this option causes the launcher
    to, in effect, split its invocation into two sub-invocations: The first does a
    training run (AOTMode=record) and then the second creates the AOT cache

    pass command-line options that apply specifically to cache creation

    Training Run

    The effectiveness of the AOT cache depends on the training run. Ideally, the
    training run should load the same classes that a production run loads when
    it starts. It may not be an easy task to create an effective training run. A
    production run may require many external dependencies, which may not be
    available in a training run. We can use mocks to simulate those dependencies,
    but may still miss some classes loaded in the production run.

    For a cache to take effect, the training run and all subsequent runs must be
    essentially similar.

    Method Profiling

    The AOT cache also collects method-execution profiles during training runs.
    When the JVM starts, it can use method-execution profiles in the cache to
    improve warmup time. The JIT compiler generates native code immediately
    upon application startup, doesn’t need to wait for profiles to be collected.

    Even with cached profiles, the HotSpot JVM continues to profile and optimize
    the application as it runs. The JIT runs earlier and with more accuracy, using
    the profiles to optimize the hot methods so that the application experiences a
    shorter warmup period.

Annotations Processing
Java developers are likely familiar with annotations in the Java language. An-
notations are metadata added to Java source code. In addition to processing
annotations at runtime using the reflection API, the Java compiler can also
process annotations at compile time. Because annotation processing by the
annotation processor may generate new Java source code, compilation of the
source code occurs after annotation processing. During compilation, javac
has three modes related to whether to compile and process annotations.

   • The first mode processes annotations first, then compiles.
   • The second mode processes annotations only, without compiling.
   • The third mode compiles only, without processing annotations.

These modes are determined by the -proc option of the javac command. The
second mode uses -proc:only, and the third mode uses -proc:none. The first
mode has been the default since JDK 6 and had no name until JDK 21, when it
was given a name, -proc:full.

Since the introduction of the annotation mechanism in JDK 6, javac’s default
behavior has been scanning the classpath for annotation processors matching
the annotations in the source code, then using the found annotation processors
to process the annotations before compiling.

This classpath scanning approach has some issues. Unintentional third-
party dependencies containing annotation processors may be present on the
classpath, and running these annotation processors can cause unexpected
problems. JDK 23 changed the default javac annotation processing strategy
from -proc:full to -proc:none, meaning that annotation processing is no
longer enabled by default. If your application relies on the default classpath
scanning mechanism to discover annotation processors during build time,
annotation processors found on the classpath will not be run in JDK 23,
impacting application builds.

Changing the default annotation processor behavior can significantly impact
the build of existing applications. Therefore, the new -proc:full option has
been backported to OpenJDK 11 and 17. If your application uses OpenJDK 11,
Annotations Processing                                                      96


17, 21, or later and relies on the default annotation processing behavior, you
can explicitly enable the previous default behavior by adding the -proc:full
option. This way, you won’t need to make changes when upgrading to newer
OpenJDK versions.

If your application’s build process doesn’t rely on the default annotation pro-
cessor behavior, no changes are required. Specifically, if javac already uses
the following options, they do not need to be modified.


   • -processor,
   • -processor-path,
   • --processor-module-path,
   • -proc.

32‐bit x86 Port
The source code and build support for the 32-bit x86 port was removed,
including Windows and Linux. The motivation is that the cost of maintaining
32-bit x86 port outweighs the benefits. Removing this port can unblock new
features that require platform-specific support from having to implement 32-
bit x86 fallbacks. The cost for implementing new features like virtual threads,
Foreign Function & Memory API (FFM), Vector API, etc. on 32-bit x86 platform
is very high.
