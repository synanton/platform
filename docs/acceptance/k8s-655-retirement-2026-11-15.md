## Live finding fixed during acceptance

The first #710 deployment proved the boundary-driven relix path, but the real
producer path exposed a gap: `PromotionOwnershipStore.insertPromotionResult`
wrote INVALID rows with `claim_status=COMPLETED`, so the relix consumer never
claimed them. The producer row had correct canonical endpoints and
`EXTRACTED_EVIDENCE_NOT_FOUND`, but no `CONTRADICTS` evidence was written.

PR #711 changes INVALID rows to `claim_status=PENDING` and adds regression
coverage. The final images above include the fix. See
[`finding-invalid-terminal.txt`](artifacts/k8s-655-retirement-2026-11-15/finding-invalid-terminal.txt).

## Regex boundary

Regex extraction emits `Concept` mentions only. Resolution uses
`ExactTypeCompatibility`, and `requires` requires
`MaintenanceSystem -> Component`; regex therefore cannot produce this canonical
relation. `GraphWriter` rejects the relation before promotion. To exercise the
deployed #655 path without changing the extraction provider or the ontology:

- V1 support was placed at the Cassandra promotion boundary (VALID row). The
  deployed relix consumer/promoter wrote the canonical `:REL` and `SUPPORTS`
  evidence.
- V2e is a **real producer-generated INVALID row**: the extracted relation and
  active resolutions were seeded, the Cassandra extraction evidence was removed,
  and the deployed synflux producer/validator produced
  `EXTRACTED_EVIDENCE_NOT_FOUND` with canonical endpoints.
- The deployed relix consumer/promoter then recorded the contradiction.

A same-canonical domain/range rejection cannot be produced by changing content
alone: the validator keys on canonical types, so the same canonical relation has
the same validity unless the ontology version changes. That was not attempted in
this environment.

| Step | Result |
|---|---|
| V1 support | `ACTIVE`, `SUPPORTS/CURRENT`, chunk `54ec5884...:0`, source `acceptance-655-probe-1794759429` |
| V2e producer row | `INVALID`, `EXTRACTED_EVIDENCE_NOT_FOUND`, canonical endpoints populated, consumer `COMPLETED` |
| After contradiction | `CONFLICTED`, `active=false`, `review_required=true`; evidence `SUPPORTS/CURRENT` + `CONTRADICTS/SUPERSEDED` (V2b) + `CONTRADICTS/CONTRADICTING` (V2e) |
| V3e replacement | same source, generation 2, revision `2c99a6b9...`; activation `CURRENT`, `source_current` generation 2 |
| After replacement | `ACTIVE`, V2e and V2b contradictions `SUPERSEDED`, V1 support `CURRENT` |

`CONTRADICTS` evidence is written as `CONTRADICTING`, not `CURRENT`; derived-state
recompute treats any non-`SUPERSEDED` contradiction as current conflict. The
materialized outcome is `CONFLICTED`, inactive, review-required.

Recovery in this scenario occurred through activation-triggered evidence
retirement/recompute. The derivation-only sweep is proven separately in
Scenario C.

## What this proves

- The deployed relix code materializes `CONTRADICTS` evidence from INVALID
  promotions with canonical endpoints and derives `CONFLICTED` (inactive,
  review-required).
- The deployed synflux producer now emits claimable INVALID rows; the deployed
  relix consumer processes them.
- A real source replacement retires contradiction evidence and restores
  `ACTIVE`.
- The derivation-only reconciler repairs drift from evidence, advances a durable
  watermark, and is idempotent.
- The new contradiction evidence remains tenant-scoped.
- Regex extraction behavior is unchanged.

## What this does not prove

- A full regex ingestion cannot produce this same-canonical relation; the V1
  boundary row and the V2e extracted-relation/resolution seeds were required.
  The upstream domain/range rejection path was not exercised.
- The INVALID reason exercised here is evidence disappearance, not a live
  ontology domain/range change.
- The sweep was triggered by its schedule, not an admin endpoint (none exists).
- Load, performance, and mixed GPU+regex extraction were not tested.
- `synquest` was not redeployed; the search read path is unchanged from
  `fe680d0f`.
