# Архитектура платформы Synanton (v1.23)

> **Document type:** окончательный инженерный справочник
> **Version:** 1.23
> **Date:** 2026-08-28
> **Status:** Утверждено (реализация ведётся)
> **Audience:** архитекторы, владельцы модулей, инженеры по безопасности, SRE
> **Related docs:** [synanton-design-1.22.md](../../docs/architecture/synanton-design-1.22.md), [план реализации поиска с учётом классификации](../../docs/implementation/classification-aware-search/INDEX.md), [демонстрация семантического поиска с учётом классификации](../../docs/demos/classification-aware-semantic-search-demo.md)
> **Revision note (2026-08-29):** §3.2–§3.5 и §3.9 пересмотрены: вместо исключения целого фрагмента используется модель original/masked-представлений, основанная на результате маскирования; см. §3.2a, §3.3, §3.4.

## 1. Мотивация

v1.22 ввёл структурированное извлечение и семантическое разбиение на фрагменты, но модель безопасности платформы по-прежнему ориентирована **на ресурсы** (`SPACE | PROJECT | FOLDER | DOCUMENT`). Она не позволяет выразить чувствительность **внутри документа**: один PDF может содержать идентификационные данные (RESTRICTED), личные контактные данные (PERSONAL) и сведения о финансовом вознаграждении (FINANCIAL), и разные роли должны иметь возможность выполнять поиск без раскрытия фрагментов с ограниченным доступом.

Обзор на уровне дизайна (`security-review-findings.md`) выявил шесть пробелов в обеспечении безопасности:

| № | Пробел | Последствие |
|---|---|---|
| 1 | Гранулярность `acl_grants` заканчивается на уровне `DOCUMENT` | Нельзя предоставить HR-доступ к разделам PERSONAL, запретив доступ к FINANCIAL |
| 2 | В модели фрагмента нет поля `classification` | Нет атрибута, по которому можно фильтровать |
| 3 | Предварительный ACL-фильтр Cuckoo работает только для `HIGH_SECURITY` | Арендаторы `STANDARD` полагаются на постфильтрацию, раскрывающую статистику терминов и число совпадений |
| 4 | Фрагменты с ограниченным доступом записываются в **семь хранилищ** до применения любых ограничений | MinIO, фрагменты Cassandra, кэш анализа, кэш эмбеддингов, Kafka (хранение ≥30 дней), поисковый индекс, граф, кэш синтеза и anomaly topic |
| 5 | `PII redaction` упоминается, но никогда не специфицируется | В §6 шаг 5 указывает его как необязательный — нет детектора, политики или контракта |
| 6 | В контрактах извлечения v1.21/v1.22 нет поверхности безопасности | Единственное упоминание — `Sanitization | Optional | redacted output` в PDF PoC |

Поэтому платформа **не может** гарантировать, что ограниченный литерал (например, SSN) никогда не будет сохранён, включён в индекс или эмбеддинг и не утечёт через побочные каналы на стороне запроса.

Это предложение устраняет пробелы моделью **поиска с учётом классификации**, работающей на уровне фрагментов, применяющей фильтрацию на этапе компиляции запроса и использующей режим **безопасного отказа при сбое** для содержимого без метки.

## 3. Подробный дизайн

### 3.1 Модель классификации и `class_grants`

**Module:** `topology` (§25)

**Goal:** выразить разрешения ролей на классы как отдельную ось, независимую от ACL ресурсов.

**Implementation:**

Добавить таблицу `class_grants`:

sql

```
CREATE TABLE class_grants (            -- topology, new
  grant_id   UUID PRIMARY KEY,
  org_id     UUID NOT NULL,
  subject_id UUID NOT NULL,
  subject_type TEXT NOT NULL,          -- USER | GROUP | ROLE
  class      TEXT NOT NULL,            -- PERSONAL | FINANCIAL | RESTRICTED | PUBLIC
  permission TEXT NOT NULL,            -- SEARCH | VIEW
  created_at TIMESTAMPTZ NOT NULL
);
```



Эффективная видимость = `resource_acl ∧ class_grants`. Принцип наименьших привилегий обеспечивается самой конструкцией: `PAYROLL` видит `FINANCIAL`, но *не* `PERSONAL`. Распространение использует существующий §11 outbox и двухфазное подтверждение; отзыв разрешения использует удаление из Cuckoo за O(1).

**Chunk field:**

Расширить схему фрагментов v1.22:

json

```
{
  "chunk_id": "…",
  "section_path": ["3. GPU Execution Plane", "3.1 GPU Gateway"],
  "classification": ["FINANCIAL"],      // new, repeated
  "page_start": 3,
  "page_end": 3,
  "source_elements": ["elem_42", "elem_43"]
}
```



**Configuration:**

yaml

```
topology:
  class_grants:
    propagation_timeout_ms: 5000
    high_security_ack_deadline_ms: 50   # reuses §11
```



### 3.2 Этап детерминированного обнаружения

**Module:** `synflux` (§17)

**Goal:** обнаруживать фрагменты с ограниченным доступом *до* любой записи в Cassandra, Kafka или поисковый индекс.

**Implementation:**

Новый этап `ClassificationDetector` выполняется **после** разбора и **до** фиксации в Cassandra (сохраняя инвариант §6 о кэше до шины). Он обрабатывает структурированные `elements`, полученные при извлечении по v1.21.

| Детектор | Шаблон | Действие |
|---|---|---|
| SSN | `\b\d{3}-\d{2}-\d{4}\b` + проверка Luhn | `RESTRICTED` |
| Телефон (США) | `\b\d{3}-\d{3}-\d{4}\b` | `PERSONAL` |
| Адрес | регулярное выражение + географический справочник | `PERSONAL` |
| Заголовки таблиц | `"Gross income"`, `"Federal tax"`, `"Salary"` | `FINANCIAL` |

Детекторы **детерминированы**, **поддаются аудиту** и **не используют GPU**. Пропуски выявляются людьми при разборе в `synreview` (§27a) для фрагментов с низкой уверенностью.

**Policy per class:**

yaml

```
synflux:
  classification:
    enabled: true
    detectors: [ssn, phone, address, table_header]
    policy:
      RESTRICTED:
        action: MASK              # MASK | DROP | QUARANTINE | ROLE:security_officer
        store_original: false     # never persist the original — see §3.2a
      PERSONAL:
        action: MASK
        store_original: true      # authorized callers may retrieve the original
      FINANCIAL:
        action: MASK
        store_original: true
    fail_mode: quarantine        # on detector error, quarantine the document
    quarantine_state: QUARANTINED
```



Результат детектора (найденные фрагменты и классы) передаётся в решение о результате маскирования в §3.2a, которое определяет, будет ли у фрагмента одно или два представления.

### 3.2a Результат маскирования и выбор представления

**Module:** `synflux` (§17)

**Goal:** определить для каждого фрагмента, создало ли маскирование второе, более чувствительное представление — и разрешено ли вообще хранить это представление.

**Implementation:**

Этап маскирования всегда вычисляет маскированный вариант содержимого фрагмента и сравнивает его с исходным:

```
detector match
      │
      ▼
apply masking policy → masked_content
      │
      ▼
masked_content == original_content ?
      │                    │
     yes                   no
      │                    │
      ▼                    ▼
SINGLE                store_original for the
representation         matched class?
(everyone gets it)     │              │
                      true           false
                        │              │
                        ▼              ▼
                     DUAL          MASKED‑ONLY
                representation    (no original ever
                (original gated    stored, for anyone)
                 by class_grants)
```

Три возможных результата:

| Результат | Условие | Что хранится | Что получает пользователь |
|---|---|---|---|
| **Single** | Маскирование ничего не изменило (в этом фрагменте не найден буквальный чувствительный фрагмент) | Одно поле `content` в каждом хранилище | Все, у кого есть доступ к ресурсу; `classification[]` сохраняется для происхождения данных и аудита, но не ограничивает поиск этого фрагмента |
| **Dual** | Маскирование изменило содержимое **и** для найденного класса задано `store_original: true` | Два поля в каждом хранилище: `content_masked` (всегда) и `content_original` (доступное только по разрешению на класс) | Пользователи с разрешением на класс получают `content_original`; остальные — `content_masked` |
| **Masked‑only** | Маскирование изменило содержимое **и** для найденного класса задано `store_original: false` (например, для `RESTRICTED`/SSN) | Только `content_masked`; original вообще не вычисляется для хранения в каком-либо хранилище | Все пользователи, включая имеющих разрешение на класс; конфигурация означает «ограничено для всех» |

Этот механизм заменяет прежнее жёстко заданное правило «исходный фрагмент никогда не записывается ни в одно хранилище» настройкой `store_original: false`, а не отдельным особым случаем. Классификация и маскирование по-прежнему оцениваются **для каждого фрагмента**: один и тот же класс `FINANCIAL` может дать результат Single для фрагмента, где в тексте лишь говорится о «программе вознаграждений руководителей», и Dual для фрагмента с самой таблицей зарплат.

**Пример маскирования фрагмента (результат Dual):**

diff

```
- "Salary: €180,000"
+ "Salary: [REDACTED:FINANCIAL]"
```



Оба варианта доступны последующим этапам; какой вариант увидит конкретное хранилище и пользователь, определяется в §3.3.

**Пример маскирования фрагмента (результат Masked‑only, `store_original: false`):**

diff

```
- "SSN: 000-00-0000"
+ "SSN: [REDACTED:SSN]"
```



`"000-00-0000"` никогда не вычисляется для сохранения — даже для пользователя с разрешением на класс RESTRICTED. Представления original, которое можно было бы ограничить, не существует.

**Доступ хранилищ (до применения ограничений):**

| Хранилище | Этап доступа | Результат Single | Результат Dual | Результат Masked‑only |
|---|---|---|---|---|
| MinIO / `synvault`, исходные байты | шаг 2 | не рассматривается в этом документе, см. §5 | не рассматривается в этом документе, см. §5 | не рассматривается в этом документе, см. §5 |
| `ingestion_cache_chunks` | шаг 3 | одно поле | `content_masked` + `content_original` | только `content_masked` |
| `ingestion_cache_analysis` | шаг 5b | одно поле | `content_masked` + `content_original` | только `content_masked` |
| `embedding_content_cache` | шаг 6 | один эмбеддинг | `embedding_masked` + `embedding_original` | только `embedding_masked` |
| Kafka `synflux_enriched_chunks` | шаг 8 | одно поле | оба поля | только `content_masked` |
| `synquest` BM25 + HNSW | шаг 9 | одно поле | оба поля; представление выбирается при запросе (§3.3) | только `content_masked` |
| граф `relix` | шаг 9 | без меток представления | сущности/рёбра помечены `representation` | только производные от `content_masked` данные |
| кэш синтеза | шаг 4 запроса | одна запись | с учётом представления и фильтрацией по пользователю | только маскированная запись |
| topic `synanton_anomaly` | шаги 13–14 запроса | передаётся без изменений | удаляется, если может раскрыть `content_original` | удаляется |

### 3.3 Выбор представления на этапе компиляции

**Module:** `gateway` (§23), `planner` (§22)

**Goal:** для фрагментов с представлением Dual (§3.2a) выбирать original или masked **до** вычисления статистики BM25/IDF и сбора кандидатов HNSW — не постфильтром и не исключением всего фрагмента.

**Implementation:**

`AclInjector` (ранее только ACL) теперь на этапе компиляции добавляет условия ACL ресурса **и** условие представления, вычисленное по `class_grants` пользователя:

java

```
// Before: Must(org_id=acme, space_id=finance)
// After:  Must(org_id=acme, space_id=finance, class IN ('FINANCIAL', 'PUBLIC'))
//         → representation = ORIGINAL for chunks classified FINANCIAL, MASKED otherwise
```



Конкретно для фрагмента Dual с классом `FINANCIAL`:

- Пользователь имеет разрешение на класс `FINANCIAL` → запрос обращается к `content_original`, `embedding_original` и рёбрам графа с `representation=original`.
- Пользователь не имеет разрешения на класс `FINANCIAL` → запрос обращается к `content_masked`, `embedding_masked` и рёбрам графа с `representation=masked`. Фрагмент **не исключается**: маскированное поле полностью доступно для поиска, но никогда не содержит чувствительный литерал.
- Для фрагментов Masked‑only (`store_original: false`) любой пользователь — независимо от разрешений на класс — получает `content_masked`, поскольку поля `original` для выбора не существует.
- Для фрагментов Single существует только одно поле; выбор представления ничего не меняет, и фрагмент доступен всем, у кого есть доступ к ресурсу.

Это применяется к:

- статистике терминов BM25 (литерал `SSN` не учитывается ни для одной роли; маскированный литерал, например сумма зарплаты, не учитывается для пользователей без разрешения, хотя окружающий маскированный текст учитывается);
- предварительному фильтру HNSW (вектор `embedding_original` не рассматривается для пользователей без разрешения);
- ACL-фильтру Cuckoo, расширенному измерением «класс → представление» для HIGH_SECURITY.

**Обязательно для всех уровней.** Предварительный фильтр Cuckoo больше не применяется только к `HIGH_SECURITY`: выбор представления выполняется и для арендаторов `STANDARD`.

**Configuration:**

yaml

```
synquest:
  classification:
    filter:
      enabled: true
      fail_closed: true          # if class field missing, treat as RESTRICTED (masked-only)

gateway:
  classification:
    enforce: true
    default_class: RESTRICTED    # unlabelled chunks → most restrictive representation
```



### 3.4 Карантин и маскирование

**Module:** `synflux` (§17)

**Goal:** обеспечить режим безопасного отказа при сбое, если детектор завершился ошибкой или уверенность низкая; это дополняет решение о представлении из §3.2a.

**Implementation:**

| Результат | Действие |
|---|---|
| Детектор вернул класс с высокой уверенностью, маскирование ничего не изменило | Представление Single (§3.2a) |
| Детектор вернул класс с высокой уверенностью, содержимое изменено маскированием, `store_original: true` | Представление Dual (§3.2a); действие `MASK` |
| Детектор вернул класс с высокой уверенностью, содержимое изменено маскированием, `store_original: false` | Представление Masked‑only (§3.2a); действие `MASK` |
| Вместо `MASK` действие политики — `DROP` или `QUARANTINE` | Фрагмент (или документ) полностью скрывается — это строже маскирования и не зависит от модели представлений |
| Ошибка детектора | `manifest.state = QUARANTINED`; фрагменты не публикуются; отправляется оповещение |
| Уверенность ниже порога | Направить в `synreview` (§27a) на проверку человеком; документ остаётся в `PENDING_REVIEW` |

**Состояние карантина в manifest:**

sql

```
-- new state value
ALTER TABLE ingestion_cache.manifest
  ADD CONSTRAINT manifest_state_check
  CHECK (state IN ('ACQUIRED', 'PARSED', 'CHUNKED', 'ENRICHED', 'EMBEDDED',
                   'INDEXED', 'QUARANTINED', 'PENDING_REVIEW'));
```



### 3.5 Распространение во все хранилища

**Обратный индекс** (§20):

Фрагмент Dual индексируется как **два поля Lucene**: `content_masked` (всегда) и `content_original` (только если §3.2a выбрал Dual). Оба поля содержат одинаковые `classification[]` и `chunk_id`. Скомпилированный запрос (§3.3) обращается ровно к одному из этих полей для каждого пользователя — никогда к обоим; следовательно, статистика терминов неавторизованного пользователя вычисляется только по `content_masked`. Фрагменты Masked‑only индексируют только `content_masked`; фрагменты Single, как и раньше, индексируют одно обычное поле `content`.

**Кэш эмбеддингов** (§18):

Ключ меняется с `(tenant, chunk_text_hash)` на `(tenant, class, representation, chunk_text_hash)`, где `representation ∈ {single, masked, original}`. Фрагмент Dual создаёт **две записи кэша и два эмбеддинга** — `embedding_masked` и `embedding_original`, поскольку исходный и маскированный тексты различаются и нельзя предполагать, что они дадут одинаковый вектор. Причина изоляции записи `original`: векторы немаскированного классифицированного текста сами классифицированы (риск инверсии). Совместное использование между арендаторами отключается для записей с классом не `PUBLIC` или представлением `original`; записи `masked` и `single` могут по-прежнему совместно использоваться между арендаторами согласно действующему правилу `PUBLIC`.

**Сущности графа** (§21):

Сущности и рёбра содержат и `classification`, и `representation`. Для фрагмента Dual извлечение сущностей выполняется один раз для `content_masked` и один раз для `content_original`; факт, присутствующий только в исходном тексте (например, сумма зарплаты), создаёт ребро с `representation=original`, отсутствующее в результате обработки masked-представления. Обход графа фильтруется по `classification` **и** выбирает `representation` так же, как поиск в §3.3: неавторизованные пользователи обходят только рёбра `representation=masked`. Фрагменты Masked‑only никогда не создают рёбра `representation=original`. Повторно используется механизм `source_ref_count` (§10, шаг 5).

**Кэш синтеза** (§23):

В `acl_mask` добавляются набор классов и маркер представления:

json

```
{
  "acl_mask": {
    "org_id": "acme",
    "class_set": ["FINANCIAL", "PUBLIC"],
    "representation": "masked"
  }
}
```



Результат синтеза, использовавший `content_original` хотя бы одного фрагмента, кэшируется с `representation: "original"` и повторно предоставляется только тем пользователям, для которых разрешения на классы позволили бы выбрать `original` для того же фрагмента. Совместное использование между арендаторами отключается для любой записи, источники которой содержат класс не `PUBLIC` или представление `original`.

**Сборка контекста LLM** (§23):

Выбор представления выполняется **до** сборки промпта по тому же решению для каждого фрагмента, что и при поиске (§3.3): в промпт попадает `content_original` только для фрагментов, доступ к которым разрешён классом пользователя, и `content_masked` в остальных случаях. Пути деградации GPU и попадания в кэш не должны обходить этот выбор.

### 3.6 Санитизация на стороне запроса

**Каналы:**

| Канал | Действие |
|---|---|
| Suggest / autocomplete | Скрывать термины, встречающиеся только в поле `content_original`, к которому пользователь не имеет доступа |
| topic `synanton_anomaly` | Удалять исходный текст запроса, если он соответствует шаблону masked‑only (например, SSN) |
| `execution_trace` | Не включать число совпадений и статистику по классам для представления `original`, если пользователь не авторизован |
| Выделенные фрагменты | Формировать из представления, выбранного для пользователя (§3.3); не подставлять `content_original` для неавторизованного пользователя |

**Implementation:** повторно использовать шаблоны `ClassificationDetector` при обработке запроса.

### 3.7 Устранение последствий

**Устранение утечки:** существующий каскад удаления GDPR (§10, p99 ≤ 45 s) удаляет содержимое из всех плоскостей. Новый `ReindexAfterPolicyChangeWorkflow` (Temporal, `control-plane`) обрабатывает смену меток при изменении политики классификации.

**Шаги рабочего процесса:**

1. Прочитать строки `manifest`, затронутые изменением политики.
2. Повторно запустить `ClassificationDetector` с новой политикой.
3. Переиндексировать фрагменты с обновлённым `classification[]`.
4. Обновить `synquest` и `relix`.

### 3.9 Контроль CI: `test:security`

**Уровень:** `test:security` (новый; выполняется для каждого PR, затрагивающего пути классификации)

**Корпус:** `demo-data/documents/restricted/` (см. Deliverable 4)

**Проверки:**

bash

```
# 1. Masked-only literal (store_original: false) appears in NO store, for ANY role
grep -r "000-00-0000" cassandra/ chunks/ kafka-payloads/ index-terms/ embedding-cache/ graph/ && exit 1

# 2. Chunk classification field is present
grep '"classification":\s*\["RESTRICTED"\]' cassandra/chunks/

# 3. Masked-only literal: exact-match search returns zero hits for every role, authorised or not
curl -H "X-Synanton-Role: hr" /search?q=SSN | jq '.hits | length' == 0

# 4. Dual-representation: unauthorised role sees the masked field, not zero hits and not the literal
curl -H "X-Synanton-Role: hr" /search?q="gross+income" | jq -r '.hits[0].snippet' | grep -q "REDACTED:FINANCIAL"

# 5. Dual-representation: authorised role sees the original value for the same chunk
curl -H "X-Synanton-Role: payroll" /search?q="gross+income" | jq -r '.hits[0].snippet' | grep -qv "REDACTED:FINANCIAL"

# 6. Single representation: unmodified chunk returns identical content to both roles
diff <(curl -H "X-Synanton-Role: hr" /search?q="compensation+program" | jq -r '.hits[0].snippet') \
     <(curl -H "X-Synanton-Role: bob" /search?q="compensation+program" | jq -r '.hits[0].snippet')
```



**Критерии прохождения:**

- Для классов с `store_original: false` (например, `RESTRICTED`/SSN) литерал отсутствует **во всех** хранилищах для любой роли: термы индекса, строки Cassandra, сообщения Kafka, кэш эмбеддингов, сущности графа, кэш синтеза.
- Для классов с `store_original: true` и результатом Dual (например, `FINANCIAL`, `PERSONAL`) поиск для неавторизованной роли возвращает фрагмент с `content_masked` (не ноль результатов и не литерал); для авторизованной роли поиск того же фрагмента возвращает `content_original`.
- Для фрагментов Single (маскирование ничего не изменило) авторизованным и неавторизованным ролям возвращается одинаковое содержимое.

## 5. Обратная совместимость и путь обновления

**Нарушающих совместимость изменений нет.** Все новые возможности включаются по выбору:

- `synflux.classification.enabled = false` (по умолчанию) — поведение приёма данных не меняется;
- `synquest.classification.filter.enabled = true` — безопасно, если поле отсутствует (во время миграции оно считается `PUBLIC`; `fail_closed` можно переключить);
- `gateway.classification.enforce = false` (по умолчанию) — существующие запросы не меняются.

**Порядок обновления:**

1. Развернуть v1.23 со всеми флагами `false`.
2. Включить детекторы для тестового арендатора.
3. Заполнить для этого арендатора `class_grants`.
4. Убедиться, что `test:security` проходит.
5. Развернуть изменение для всех арендаторов.

**Остаточный риск:** исходный PDF в `synvault` сохраняет SSN. Это **преднамеренно**: хранение исходных объектов не относится к поисковой системе и защищено отдельным шифрованием и разрешениями `content:read`. Для развёртываний, которым требуется санитизация данных при хранении, можно настроить конвейер санитизации до приёма данных (вне области v1.23). В самой поисковой плоскости эквивалентную гарантию для содержимого RESTRICTED/SSN обеспечивает политика `store_original: false` (§3.2a): литерал вообще не вычисляется для сохранения, независимо от разрешений пользователя на классы.

## 7. Открытые вопросы

1. **Порог уверенности детектора.** Какой уровень ложноположительных срабатываний допустим для обнаружения RESTRICTED? Предложение: начать с 0,1% и настраивать по результатам обратной связи `synreview`.
2. **Совместное использование между арендаторами.** Следует ли оставить возможность совместного использования фрагментов класса `PUBLIC`? Да — это сохраняет поведение v1.22 для несекретного содержимого.
3. **Хранение исходного PDF.** Следует ли предложить конвейер санитизации до приёма данных? Вне области v1.23; это документированная настройка развёртывания.
4. **Контекстная классификация (не по буквальному совпадению).** Следует ли считать фрагмент, унаследовавший класс из контекста раздела, но не содержащий буквального фрагмента, изменённого маскированием, представлением Single и показывать его всем (как указано здесь), или некоторым развёртываниям нужна возможность требовать Dual/Masked‑only только на основании классификации контекста? Решение v1.23: Single, как определено в §3.2a; вернуться к вопросу, если обратная связь `synreview` покажет утечку чувствительных выводов при классификации только по контексту.

## 8. Заключение

v1.23 вводит модель **семантического поиска с учётом классификации**, которая устраняет выявленный при обзоре дизайна пробел безопасности внутри документов. Добавляя поле `classification[]` во фрагменты, детерминированные детекторы при приёме данных, выбор представления original/masked по результату маскирования (§3.2a), выбор представления при компиляции запроса и безопасный отказ при сбое для содержимого без метки, платформа гарантирует: содержимое, не затронутое маскированием, доступно всем; содержимое, изменённое маскированием, доступно всем в masked-виде и пользователям с разрешённым классом в original-виде; содержимое класса, для которого задано `store_original: false` (например, SSN/`RESTRICTED`), **никогда не хранится, не индексируется, не включается в эмбеддинг и не раскрывается** в исходном виде никому.

Дизайн **дополняющий**, **не нарушает совместимость** и **безопасен для отката**. Все новые возможности включаются по выбору; безопасные значения по умолчанию сохраняют поведение v1.22.
