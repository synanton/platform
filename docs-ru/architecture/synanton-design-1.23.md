  > **Статус:** Одобрено (внедрение в процессе)
  > **Целевая аудитория:** Архитекторы, владельцы модулей, инженеры по безопасности, SRE-специалисты
  > **Связанная документация:** [synanton-design-1.22.md](./synanton-design-1.22.md), [план реализации поиска с учетом классификации](../implementation/classification-aware-search/INDEX.md), [демонстрация семантического поиска с учетом классификации](../demos/classification-aware-semantic-search-demo.md)
  > **Примечание о пересмотре (29.08.2026):** Разделы 3.2–3.5 и 3.9 пересмотрены: вместо исключения целых фрагментов используется модель **исходного/замаскированного представления**, основанная на результатах маскировки — см. 3.2a, 3.3, 3.4.

  ## 1. Мотивация

  В версии 1.22 были введены структурированное извлечение и семантическое сегментирование, но модель безопасности платформы остается **ресурсоцентричной ‑** («ПРОСТРАНСТВО | ПРОЕКТ | ПАПКА | ДОКУМЕНТ»). Она не может отображать ‑конфиденциальность **поддокументов** — один PDF-файл, содержащий данные об идентификации (RESTRICTED), личных контактных данных (PERSONAL) и финансовом вознаграждении (FINANCIAL), должен быть доступен для поиска различными ролями без раскрытия ограниченных областей.

  проектирования ‑(«security-review-findings.md») выявил шесть пробелов в обеспечении соблюдения требований:

  | #    | Разрыв                                                       | Последствия                                                  |
  | ---- | ------------------------------------------------------------ | ------------------------------------------------------------ |
  | 1    | Детализация `acl_grants` заканчивается на `DOCUMENT`         | Невозможно предоставить HR доступ к разделам PERSONAL, одновременно запрещая доступ к разделу FINANCIAL |
  | 2    | В модели Chunk отсутствует поле `classification`             | Фильтруемый атрибут отсутствует                              |
  | 3    | фильтр ‑ACL Cuckoo работает ‑только с уровнем безопасности `HIGH_SECURITY` | Арендаторы уровня `STANDARD` полагаются на последующий ‑фильтр, который раскрывает статистику терминов и количество срабатываний |
  | 4    | Ограниченные диапазоны записываются в **семь хранилищ** перед любыми воротами | MinIO, фрагменты Cassandra, кэш анализа, кэш встраивания, Kafka (срок хранения ≥30 дней), индекс поиска, граф, кэш синтеза, тема аномалий |
  | 5    | «Засекречивание персональных данных» названо, но не указано  | §6 шаг 5 указывает, что это необязательно — нет детектора, политики или контракта |
  | 6    | Контракты извлечения v1.21/v1.22 не имеют поверхности безопасности | Единственное упоминание — «Очистка                           |

  Таким образом, платформа **не может** гарантировать, что ограниченный текст (например, номер социального страхования) никогда не будет сохранен, проиндексирован, встроен и не будет передан через ‑каналы обработки запросов.

  модель поиска с учетом ‑классификации , которая работает с детализацией на уровне фрагментов, обеспечивает ‑фильтрацию на этапе компиляции и предоставляет ‑значение по умолчанию «закрыть при ошибке» для немаркированного контента.

  ## 3. Детальное проектирование

  ### 3.1 Модель классификации и `class_grants`

  **Модуль:** `topology` (§25)

  **Цель:** Выделить права доступа ‑к ролям и ‑классам в отдельную ось, не связанную с ACL ресурсов.

  **Выполнение:**

  Добавьте таблицу `class_grants`:

  ```sql
  CREATE TABLE class_grants (            -- topology, new
    grant_id   UUID PRIMARY KEY,
    org_id     UUID NOT NULL,
    subject_id UUID NOT NULL,
    subject_type TEXT NOT NULL,          -- USER | GROUP | ROLE
    class      TEXT NOT NULL,            -- PERSONAL | FINANCIAL | RESTRICTED | PUBLIC
    permission TEXT NOT NULL,            -- SEARCH | VIEW
    created_at TIMESTAMPTZ NOT NULL
  );
  ```

  

  Эффективная видимость вычисляется как пересечение `resource_acl ∧ class_grants`. Пприменяется принцип наименьших привилегий: `PAYROLL` видит `FINANCIAL`, а *не* `PERSONAL`. Перерасчет при обновлении повторно использует исходящий поток  §11 + двухфазный ‑путь подтверждения; отзыв повторно использует удаление O(1) Cuckoo delete.

  **Поля фрагмента:**

  Расширьте схему фрагментов текста v1.22:

  ```json
  {
    "chunk_id": "…",
    "section_path": ["3. GPU Execution Plane", "3.1 GPU Gateway"],
    "classification": ["FINANCIAL"],      // new, repeated
    "page_start": 3,
    "page_end": 3,
    "source_elements": ["elem_42", "elem_43"]
  }
  ```

  **Конфигурация:**

  ```yaml
  topology:
  class_grants:
  propagation_timeout_ms: 5000
  high_security_ack_deadline_ms: 50 # повторно использует §11
  ```

  

  ### 3.2 Этап детерминированного детектора

  **Модуль:** `synflux` (§17)

  **Цель:** обнаружение ограниченных диапазонов *до* любой записи в Cassandra, Kafka или поисковый индекс.

  **Выполнение:**

  Новый этап `ClassificationDetector` запускается **после** парсинга и **перед** фиксацией изменений в Cassandra (сохраняя  §6 cache‑before‑bus инвариант). Он работает со структурированными `элементами` из версии 1.21.

  | Детектор         | Шаблон                                           | Класс        |
  | ---------------- | ------------------------------------------------ | ------------ |
  | Номер SSN        | `\b\d{3}-\d{2}-\d{4}\b` + ‑проверка Луна         | `RESTRICTED` |
  | Телефон (США)    | `\b\d{3}-\d{3}-\d{4}\b`                          | `PERSONAL`   |
  | Адрес            | регулярное выражение + географический справочник | `PERSONAL`   |
  | Заголовки таблиц | Валовый доход, Налог, Заработная плата           | `FINANCIAL`  |

  Детекторы являются **детерминированными**, **проверяемыми** и не требуют использования GPU. Пропуски выявляются путем проверки человеком в рамках процедуры `synreview` (§27a) при низких значениях доверительного интервала.

  **Правила для каждого класса:**

  ```yaml
  synflux:
    classification:
      enabled: true
      detectors: [ssn, phone, address, table_header]
      policy:
        RESTRICTED:
          action: MASK              # MASK | DROP | QUARANTINE | ROLE:security_officer
          store_original: false     # never persist the original — see §3.2a
        PERSONAL:
          action: MASK
          store_original: true      # authorized callers may retrieve the original
        FINANCIAL:
          action: MASK
          store_original: true
      fail_mode: quarantine        # on detector error, quarantine the document
      quarantine_state: QUARANTINED
  ```

  

  Выходные данные детектора (соответствующие фрагменты и классы) используются для принятия ‑решения о результате маскирования в §3.2a, которое определяет, получит ли фрагмент одно или два представления.

  ### 3.2a Решение о результатах маскирования и представлении 

  **Модуль:** `synflux` (§17)

  **Цель:**  определить для каждого фрагмента, создало ли маскирование второе, более важное представление, и разрешено ли вообще хранить это представление в памяти.

  **Реализация:**

  На этапе маскирования вычисляется маскированная форма фрагмента и сравнивается с оригиналом:

  ```
  детектор совпадений
          │
          ▼
  применить политику маскирования → замаскированное_содержимое
          │
          ▼
    маскированный контент совпалает с оригиналом?
          │                  │
          да                 нет
          │                  │
          ▼                  ▼
      БЕЗ МАСКИ    присутствует store_original флаг?
       (SINGLE)      │                       │
                     да                     нет
                     │                       │
                     ▼                       ▼
         DUAL          MASKED‑ONLY
   
  ```

  Три возможных результата:

  | Результат       | Когда                                                        | Что хранится                                                 | Кто что получает                                             |
  | --------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
  | **SINGLE**      | Маскирование не вносит изменений                             | Одно поле `content` на хранилище                             | Все, кто имеет доступ к ресурсам, — `classification[]` сохраняется для проверки происхождения/аудита, но не ограничивает получение этого фрагмента |
  | **DUAL**        | Маскирование изменяет содержимое и значение `store_original: true` соответствующего класса | Два поля в хранилище: `content_masked` и `content_original` ( доступ ограничен) | Авторизованные классы пользователей получают `content_original`; все остальные получают `content_masked` |
  | **MASKED‑ONLY** | Маскировка изменяет содержимое **и** значение `store_original: false` соответствующего класса (например, `RESTRICTED`/SSN) | Только `content_masked` — исходное значение не  для хранится | Всем, включая ‑авторизованных вызывающих пользователей класса —   "ограничено для всех" |

  Это позволяет рассматривать ранее существовавшее  заданное правило "исходный фрагмент никогда не записывается ни в одно хранилище" как одну настройку (`store_original: false`)  единого механизма, а не как частный случай. Классификация и маскирование по-прежнему оцениваются **для каждого фрагмента**: один и тот же класс `FINANCIAL` может выдавать результат Single для фрагмента, в котором в тексте упоминается только «программа вознаграждения руководителей», и результат Dual для фрагмента, содержащего фактическую таблицу заработной платы.

  **Пример маскирования области действия (двойной результат):**

  ```diff
  — "Зарплата: 180 000 руб"
  + "Зарплата: [REDACTED:FINANCIAL]"
  ```

  Обе формы доступны для дальнейшего использования; какая именно форма будет видна конкретному пользователю, регулируется §3.3.

  только результат маскирования , `store_original: false`):**‑

  ```diff
  - "SSN: 000-00-0000"
  + "SSN: [REDACTED:SSN]"
  ```

  

  Значение `"000-00-0000"` никогда не используется для хранения  (даже для пользователся, имеющей права доступа класса `RESTRICTED`. Нет никакого исходного текста, который можно было бы использовать.

  **Доступность данных в хранилищах:**

  | Хранилище                               | Этап               | Представление без изменений         | Двойное представдение                                       | Представление только с маскированием |
  | --------------------------------------- | ------------------ | ----------------------------------- | ----------------------------------------------------------- | ------------------------------------ |
  | MinIO / необработанные байты `synvault` | шаг 2              | н/д — вне области видимости, см. §5 | н/д — вне области видимости, см. §5                         | н/д — вне области видимости, см. §5  |
  | `ingestion_cache_chunks`                | шаг 3              | одно поле                           | `content_masked` + `content_original`                       | только `content_masked`              |
  | `ingestion_cache_analysis`                   | шаг 5b             | одно поле                           | `content_masked` + `content_original`                 | только `content_masked`            |
  | `embedding_content_cache`               | шаг 6              | одно встраивание                    | `embedding_masked` + `embedding_original`                   | только `embedding_masked`            |
  | `synflux_enriched_chunks` Kafka         | шаг 8              | одно поле                           | оба поля                                                    | только `content_masked`              |
  | `synquest` BM25 + HNSW                  | шаг 9              | одно поле                           | оба поля, представление выбрано во время запроса (§3.3)     | только `content_masked`              |
  | Граф `relix`                            | Шаг 9              | без тегов                           | сущности/ребра, помеченные тегом `representation`           | `content_masked` ‑только производные |
  | кэш синтеза                             | шаг запроса 4      | одна запись                         | ‑учитывает представление, фильтруется по вызывающей стороне | только замаскированная запись        |
  | Тема `synanton_anomaly`                 | Шаги запроса 13–14 | сквозная передача                   | удалено, когда это позволило бы выявить `content_original`  | удалено                              |

  ### 3.3 Выбор представления на этапе компиляции

  **Модули:** `gateway` (§23), `planner` (§22)

  **Цель:** Для фрагментов с двойным представлением (§3.2a) выбирать «исходный» против «замаскированного» **до** вычисления статистики BM25/IDF или сбора кандидатов HNSW — не в качестве постфильтра ‑и не для ‑исключения всего фрагмента.

  **Выполнение:**

  `AclInjector` (ранее ‑только ACL) теперь добавляет пункты ACL для ресурсов **и** пункт представления на этапе компиляции, который выводится из `class_grants` вызывающей стороны:

  java

  ```
  // Перед этим: Must(org_id=acme, space_id=finance)
  // После: Must(org_id=acme, space_id=finance, class IN ('FINANCIAL', 'PUBLIC'))
  // → representation = ORIGINAL для фрагментов, классифицированных как FINANCIAL, MASKED в противном случае
  ```

  

  Конкретно, для блока двойного ‑представления, классифицированного как `FINANCIAL`:

  - Вызывающий объект имеет грант класса `FINANCIAL` → запрос нацелен на ребра графа `content_original` / `embedding_original` / `representation=original`.
  - У вызывающего объекта нет разрешения класса `FINANCIAL` → запрос нацелен на ребра графа `content_masked` / `embedding_masked` / `representation=masked`. Фрагмент **не исключен** — замаскированное поле полностью доступно для поиска, оно просто никогда не содержит конфиденциальный литерал.
  - Для ‑фрагментов, содержащих только маскировку (`store_original: false`), каждый вызывающий объект — независимо от предоставленных прав доступа к классу — разрешается в `content_masked`, поскольку поле `original` для выбора отсутствует.
  - Для ‑блоков с одним представлением имеется только одно поле; выбор представления не является ‑операцией, и блок доступен всем, кто имеет доступ к ресурсам.

  Это достигает:

  - Статистика терминов BM25 (буквальный `SSN` никогда не учитывается ни для одной роли; замаскированный литерал, такой как цифра заработной платы, никогда не учитывается для несанкционированных ролей, хотя окружающий замаскированный текст все равно учитывается).
  - Предварительный фильтр HNSW ‑(вектор `embedding_original` никогда не рассматривается для неавторизованных ролей)
  - Фильтр ACL Cuckoo (расширенный измерением «класс → представление» для HIGH_SECURITY)

  **Обязательно для всех уровней.** Предварительный фильтр Cuckoo ‑больше не ограничивается ‑только уровнем `HIGH_SECURITY` — выбор представления теперь обязателен и для арендаторов уровня `STANDARD`.

  **Конфигурация:**

  ```yaml
  synquest:
    classification:
      filter:
        enabled: true
        fail_closed: true          # if class field missing, treat as RESTRICTED (masked-only)
  
  gateway:
    classification:
      enforce: true
      default_class: RESTRICTED    # unlabelled chunks → most restrictive representation
  ```

  

  ### 3.4 Карантин / Маскирование

  **Модуль:** `synflux` (§17)

  **Цель:** Обеспечить возможность закрытия пути обработки ошибок детектора в случае низкой достоверности результатов, помимо решения, принятого в соответствии с §3.2a.

  **Выполнение:**

  | Результат                                                    | Действие                                                     |
  | ------------------------------------------------------------ | ------------------------------------------------------------ |
  | Детектор возвращает ‑класс с высокой степенью достоверности, маскирование не изменено | Единое представление (§3.2a)                                 |
  | Детектор возвращает ‑класс с высокой степенью достоверности, маскируя измененное содержимое, `store_original: true` | Двойное представление (§3.2a); действие `MASK`               |
  | Детектор возвращает ‑класс с высокой степенью достоверности, маскируя измененное содержимое, `store_original: false` | ‑Только замаскированное представление (§3.2a); действие `MASK` |
  | В качестве меры политики используется `DROP` или `QUARANTINE` вместо `MASK` | Фрагмент (или документ) полностью скрыт — более строгий подход, чем маскирование, и не зависит от описанной выше модели представления |
  | Ошибка детектора                                             | `manifest.state = QUARANTINED`; фрагмент не опубликован; срабатывает оповещение |
  | Уровень уверенности ниже порогового значения                 | Перенаправление на «синхронную проверку» (§27a) для рассмотрения человеком; документ остается в состоянии «PENDING_REVIEW» |

  **Проявленное состояние карантина:**

  sql

  ```
  -- новое значение состояния
  ALTER TABLE ingestion_cache.manifest
  ADD CONSTRAINT manifest_state_check
  CHECK (state IN ('ACQUIRED', 'PARSED', 'CHUNKED', 'ENRICHED', 'EMBEDDED',
  'INDEXED', 'QUARANTINED', 'PENDING_REVIEW'));
  ```

  

  ### 3.5 Распространение данных во все хранилища

  **Обратный указатель** (§20):

  с двойным ‑представлением индексируется как **два поля Lucene**: `content_masked` (всегда) и `content_original` (только когда §3.2a разрешает Dual). Оба содержат одинаковые `classification[]` и `chunk_id`. Скомпилированный запрос (§3.3) нацелен ровно на одно из двух полей для каждого вызывающего объекта — никогда на оба, поэтому статистика терминов для неавторизованного вызывающего объекта вычисляется исключительно по `content_masked`. ‑Блоки только с маскировкой индексируют только `content_masked`; ‑блоки с одинарным представлением индексируют одно обычное поле `content`, как и раньше.

  **Встраивание кэша** (§18):

  Ключевые изменения: вместо `(tenant, chunk_text_hash)` используется `(tenant, class, representation, chunk_text_hash)`, где `representation ∈ {single, masked, original}`. Двойной фрагмент создает **две записи в кэше и два эмбеддинга** — `embedding_masked` и `embedding_original` — поскольку замаскированный и исходный текст различаются и не должны считаться эмбеддингами одного и того же вектора. Обоснование изоляции записи `original`: векторы незамаскированного классифицированного текста сами по себе классифицированы (риск инверсии). Совместное ‑использование между арендаторами отключено для любой записи, ключом которой является не ‑`PUBLIC` класс или `original` представление; записи `masked` и `single` по-прежнему могут использоваться между ‑арендаторами в соответствии с существующим правилом `PUBLIC`.

  **Графические сущности** (§21):

  Сущности и ребра содержат как классификацию, так и представление. Для двойного фрагмента извлечение сущности выполняется один раз для `content_masked` и один раз для `content_original`; факт, существующий только в исходном тексте (например, значение зарплаты), создает ребро с меткой `representation=original`, отсутствующее в извлечении `masked`. Обход графа фильтрует по `classification` **и** выбирает `representation` так же, как это делается в §3.3 для поиска — неавторизованные вызывающие стороны обходят только ребра `representation=masked`. ‑Фрагменты только с маскировкой никогда не создают ребра `representation=original`. Повторно используется механизм `source_ref_count` (§10, шаг 5).

  **Кэш синтеза** (§23):

  `acl_mask` получает набор классов и маркер представления:

  ```json
  {
      "acl_mask": {
          "org_id": "acme",
          "class_set": ["FINANCIAL", "PUBLIC"],
          "representation": "masked"
      }
  }
  ```

  

  Результат синтеза, основанный на `content_original` любого фрагмента, кэшируется с `representation: "original"` и воспроизводится только для вызывающих сторон, чьи разрешения классов позволили бы преобразовать тот же фрагмент в `original`. Повторное ‑использование между арендаторами отключено для любой записи, источники которой содержат не ‑`PUBLIC` класс или представление `original`.

  **Сборка контекста LLM** (§23):

  Выбор представления происходит **до** сборки запроса, используя то же ‑решение для каждого фрагмента, что и при поиске (§3.3): запрос получает `content_original` только для фрагментов, ‑к которым вызывающий класс имеет право доступа, в противном случае — `content_masked`. Пути с низкой производительностью GPU ‑и ‑попадания в кэш не должны его пропускать.

  ### 3.6 Санитаризация на стороне запроса

  **Каналы:**

  | Канал                      | Действие                                                     |
  | -------------------------- | ------------------------------------------------------------ |
  | Подсказки / автозаполнение | Подавлять термины, которые встречаются только в поле `content_original`, которое вызывающая сторона не может разрешить |
  | Тема `synanton_anomaly`    | Удалять необработанный текст запроса, если он соответствует только замаскированному ‑шаблону (например, номер социального страхования) |
  | `execution_trace`          | Опустить количество попаданий и ‑статистику по классам для исходного представления при отсутствии авторизации |
  | Выделение фрагментов       | Отображение из представления, фактически выбранного для вызывающей стороны (§3.3) — никогда не возвращаться к `content_original` для несанкционированного фрагмента |

  **Реализация:** Повторное использование шаблонов `ClassificationDetector` во время выполнения запроса.

  ### 3.7 Очистка

  **Исправление утечек:** Существующий каскад удаления данных в соответствии с GDPR (§10, стр. 99 ≤ 45 s) удаляет контент из всех плоскостей. Новый `ReindexAfterPolicyChangeWorkflow` (временный, `control-plane`) обрабатывает перемаркировку при изменении политики классификации.

  **Этапы рабочего процесса:**

  1. Прочитайте строки в списке, затронутые изменением политики.
  2. Повторно ‑запустите `ClassificationDetector` с новой политикой.
  3. Переиндексировать ‑фрагменты с обновленным массивом `classification[]`.
  4. Обновите `synquest` и `relix`.

  ### 3.9 CI Gate: `test:security`

  **Уровень:** `test:security` (новый, запускается при каждом запросе на слияние, затрагивающем пути классификации)

  **Корпус:** `demo-data/documents/restricted/` (см. Результат 4)

  **Утверждения:**

  баш

  ```
  # 1. Литерал, содержащий только маску (store_original: false), отсутствует в любом хранилище для любой роли.
  grep -r "000-00-0000" cassandra/ chunks/ kafka-payloads/ index-terms/ embedding-cache/ graph/ && exit 1
  
  # 2. Поле классификации фрагментов присутствует.
  grep '"classification":\s*\["RESTRICTED"\]' cassandra/chunks/
  
  # 3. Только замаскированный литерал: поиск с точным совпадением не возвращает ни одного результата для любой роли, авторизованной или нет.
  curl -H "X-Synanton-Role: hr" /search?q=SSN | jq '.hits | length' == 0
  
  # 4. Двойное представление: неавторизованная роль видит замаскированное поле, а не нулевое количество совпадений и не буквальное значение.
  curl -H "X-Synanton-Role: hr" /search?q="gross+income" | jq -r '.hits[0].snippet' | grep -q "REDACTED:FINANCIAL"
  
  # 5. Двойное представление: авторизованная роль видит исходное значение для того же фрагмента.
  curl -H "X-Synanton-Role: payroll" /search?q="gross+income" | jq -r '.hits[0].snippet' | grep -qv "REDACTED:FINANCIAL"
  
  # 6. Единое представление: неизмененный фрагмент возвращает идентичное содержимое обеим ролям.
  diff <(curl -H "X-Synanton-Role: hr" /search?q="compensation+program" | jq -r '.hits[0].snippet') \
  <(curl -H "X-Synanton-Role: bob" /search?q="compensation+program" | jq -r '.hits[0].snippet')
  ```

  

  **Критерии прохождения:**

  - Классы с `store_original: false` (например, `RESTRICTED`/SSN): литерал встречается в **нуле** хранилищах для каждой роли — терминов индекса, строк Cassandra, полезных нагрузок Kafka, кэша встраивания, сущностей графа, кэша синтеза.
  - Классы с `store_original: true` и результатом типа Dual (например, `FINANCIAL`, `PERSONAL`): поиск для неавторизованной роли возвращает фрагмент с `content_masked` (не ноль совпадений, не литерал); поиск для авторизованной роли по тому же фрагменту возвращает `content_original`.
  - ‑Фрагменты с одним результатом (маскирование не внесло изменений) возвращают идентичное содержимое авторизованным и неавторизованным ролям.

  ## 5. Обратная совместимость и путь обновления

  **Никаких критических изменений.** Все новые функции активируются по ‑желанию:

  - `synflux.classification.enabled = false` (по умолчанию) — поведение при приеме пищи остается неизменным
  - `synquest.classification.filter.enabled = true` — безопасно, если поле отсутствует (в процессе миграции рассматривается как `PUBLIC`; `fail_closed` можно переключить).
  - `gateway.classification.enforce = false` (по умолчанию) — существующие запросы остаются без изменений

  **Обновление в процессе эксплуатации:**

  1. Разверните версию 1.23 со всеми флагами `false`.
  2. Включите детекторы в тестовом экземпляре.
  3. Задайте начальное значение параметра `class_grants` для этого арендатора.
  4. Убедитесь, что тест `test:security` пройден успешно.
  5. Внедрить для всех арендаторов.

  **Остаточный риск:** В исходном PDF-файле в `synvault` сохраняется номер социального страхования (SSN). Это **преднамеренно** — ‑хранилище необработанных объектов находится вне системы поиска и защищено отдельным шифрованием + правами доступа `content:read`. Для развертываний, требующих проверки содержимого в состоянии покоя, ‑можно настроить конвейер предварительной проверки перед загрузкой (это выходит за рамки версии 1.23). В самой плоскости поиска эквивалентной гарантией для содержимого с флагом `RESTRICTED`/SSN является параметр политики `store_original: false` (§3.2a) — литерал никогда не вычисляется для хранения, независимо от прав доступа класса вызывающего объекта.

  ## 7. Открытые вопросы

  1. **Порог достоверности детектора.** Каков допустимый ‑уровень ложноположительных результатов для обнаружения в режиме `RESTRICTED`? Предложение: начать с 0,1% ложноположительных результатов, настроить с помощью обратной связи от `synreview`.
  2. ** ‑Совместное использование между арендаторами.** Должны ли фрагменты класса `PUBLIC` ‑оставаться доступными для совместного использования между арендаторами? Да — сохраняется поведение версии 1.22 для неконфиденциального ‑контента.
  3. **Сохранение исходных PDF-файлов.** Должна ли платформа предлагать ‑конвейер предварительной очистки перед загрузкой? Это выходит за рамки версии 1.23; задокументировано как ‑решение, принимаемое на этапе развертывания.
  4. **Контекстная (небуквальная ‑) классификация.** Следует ли рассматривать фрагмент, наследующий класс от контекста раздела, но не содержащий буквального фрагмента, который фактически изменила маскировка, как единое представление и показывать его всем (как указано здесь), или же некоторые развертывания должны иметь возможность требовать ‑поведения только с двойным/маскированным представлением исключительно на ‑уровне контекстной классификации? Решение для версии 1.23: единое представление, как решено в §3.2a; пересмотреть, если обратная связь от `synreview` покажет, что ‑классификация только по контексту приводит к утечке конфиденциальной информации.

  ## 8. Заключение

  В версии 1.23 представлена модель **семантического поиска с учетом классификации**, которая устраняет ‑выявленный в ходе анализа проекта пробел в безопасности поддокументов. Благодаря добавлению поля `classification[]` к фрагментам, детерминированным детекторам при загрузке, ‑решению о представлении исходного/замаскированного содержимого на основе ‑результата маскирования (§3.2a), ‑выбору представления во время компиляции и закрытию ‑по умолчанию при сбое для немаркированного контента, платформа гарантирует, что: контент, не затронутый маскированием, доступен всем; контент, который изменяется при маскировании, доступен всем в замаскированном виде и ‑авторизованным вызывающим сторонам класса в исходном виде; и контент, класс которого настроен как `store_original: false` (например, SSN/`RESTRICTED`), **никогда не сохраняется, не индексируется, не встраивается и не утекает** в своем исходном виде для всех.

  Конструкция является **аддитивной**, **не ‑нарушающей совместимость** и ** ‑безопасной для отката**. Все новые функции являются необязательными ‑, с безопасными настройками по умолчанию, сохраняющими поведение версии 1.22.
