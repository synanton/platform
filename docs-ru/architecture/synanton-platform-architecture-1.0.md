## 1. Краткое изложение

Synanton Platform 1.0 объединяет архитектуру, разработанную в рамках Designs 1.22–1.34.

Design [1.22](../../docs/architecture/synanton-design-1.22.md) остаётся **базовым архитектурным документом**. Design [1.23](../../docs/architecture/synanton-design-1.23.md) — **нормативная основа безопасности и представления данных**. Design 1.24 не публиковался отдельно; его материал об аннотациях, производных знаниях и пересчёте объединён с Design [1.25](../../docs/architecture/synanton-design-1.25.md).

Designs [1.26](../../docs/architecture/synanton-design-1.26.md)–[1.33](../../docs/architecture/synanton-design-1.33.md) расширяют базовую архитектуру явными контрактами Content Cache, событий и рабочих процессов, приёма данных, идентификации, среды выполнения ИИ, поиска, API и жизненного цикла Kubernetes.

Design [1.34](../../docs/architecture/synanton-design-1.34.md) добавляет межплоскостную возможность **временного версионирования и поиска на заданный момент времени**: семантику исторических версий источников, публикации/наблюдения/действительности и временную допустимость результатов поиска. Ответственность распределена между уже существующими владельцами (Ingestion 1.28, Knowledge 1.25, Search 1.31), а не передана новому владельцу (см. §10).


## 2. Архитектурный тезис

Synanton разделяет:

> **Что поступило на платформу → что понимает Synanton → как проецируются знания → кто может получить к ним доступ → как выполняются вычисления → как координируются изменения → как измеряются знания → как эксплуатируется инфраструктура.**

Основное правило владения авторитетными данными:

```text
Source state        → Ingestion 1.28
Content artifacts   → Content Cache 1.26
Canonical knowledge → Knowledge 1.25
Identity            → Identity 1.29
Authorization       → Security 1.23
AI execution        → AI Runtime 1.30
Search projections  → Search 1.31
Async coordination  → Eventing/Workflow 1.27
External contract   → Platform API 1.32
Lifecycle           → Kubernetes operators 1.33
Analytics           → derived observation
```

## 4. Нормативные инварианты

### Безопасность

1. Design 1.23 является нормативным для безопасности.
2. Аутентификация никогда не подразумевает авторизацию.
3. Классификация сама по себе не является авторизацией.
4. Маскирование — преобразование представления.
5. Контекст безопасности нельзя ослаблять на асинхронных границах.
6. Область арендатора задаётся явно и считается доверенной только после проверки.
7. При неоднозначном состоянии безопасности применяется отказ в доступе (fail-closed).
8. Чувствительные к безопасности кэши и проекции инвалидируются или обрабатываются повторно при изменении исходных предположений.

### Данные и знания

9. Идентичность источника отличается от дайджеста содержимого.
10. Канонические знания остаются авторитетными.
11. Поиск, кэш и аналитика — производные состояния.
12. Для производного состояния обязательно происхождение данных.
13. Существенная обработка производных данных фиксируется в записях запусков обработки.
14. Зависимости образуют явную модель, пригодную для анализа влияния изменений.
15. Resolutor определяет затронутое производное состояние.
16. Equalix координирует управляемый пересчёт.

### Взаимодействие

17. События — неизменяемые факты.
18. Команды выражают намерение.
19. По умолчанию используется доставка «как минимум один раз».
20. Потребители идемпотентны.
21. Большие полезные нагрузки передаются по ссылке.
22. Состояние рабочего процесса долговечно.
23. Воспроизведение явно классифицируется.

### API

24. Platform API 1.32 — стабильная внешняя граница.
25. Внутренняя топология хранилища, брокера, рабочего процесса и среды выполнения не является публичным контрактом.
26. Принятие длительной работы означает наличие долговечного состояния Operation.
27. Состояния ресурса и Operation различаются.
28. Пагинация учитывает контекст безопасности.
29. Нарушающие совместимость изменения требуют явного версионирования.

### ИИ и поиск

30. Платформа владеет семантикой выполнения ИИ; среда выполнения владеет механизмами выполнения.
31. Версия модели и дайджест артефакта являются данными о происхождении.
32. Поисковые индексы — производные проекции.
33. Безопасность — обязательное условие допустимости кандидата для поиска.
34. Ранжирование результатов поиска не может отменять авторизацию.
35. Поколения проекций воспроизводимы.
36. События, пришедшие не по порядку, не могут откатить состояние поиска.

### Kubernetes

37. Доменные контракты не требуют Kubernetes.
38. Операторы управляют жизненным циклом, а не бизнес-логикой.
39. У каждой независимо эксплуатируемой инфраструктурной плоскости есть один владелец жизненного цикла.
40. CRD — ресурсы плоскости управления жизненным циклом, а не публичные доменные API.
41. Инфраструктура GPU физически изолирована от основной платформы.
42. Согласование состояния оператора идемпотентно и приводит систему к целевому состоянию.

### Временные аспекты

Сокращённый перечень из 29 инвариантов Design 1.34 (полный список — в `synanton-design-1.34.md` §41); приведены инварианты с наиболее широкими межплоскостными последствиями.

43. Идентичностью серии версий владеет Ingestion 1.28; Knowledge 1.25 и Search 1.31 используют её, не создавая конкурирующую копию.
44. Версия источника неизменяема; исправления не меняют её.
45. Время публикации, наблюдения и действительности различаются и не сводятся к одной временной отметке.
46. `current` может быть множеством независимо допустимых версий источника, а не одной глобальной версией.
47. Перекрывающиеся или конфликтующие периоды действительности сохраняются и отмечаются, но не разрешаются молча.
48. Перед запуском последующей обработки исправления классифицируются как затрагивающие только метаданные или содержимое; только исправления содержимого запускают пересчёт через Resolutor/Equalix.
49. Временная фильтрация выполняется до ранжирования и объединяется с допустимостью по безопасности как ограничение поиска до ранжирования (инвариант 33).
50. При историческом запросе система не подменяет историческое содержимое текущим; отсутствующее или удалённое историческое состояние возвращается как явное состояние ошибки.

## 5. Сквозной жизненный цикл

```text
External Source
   │
   ▼
Ingestion 1.28
   │  SourceIdentity / SourceVersion / provenance
   │  VersionSeries (1.34): published_at / observed_at / valid_from / valid_to
   ▼
Content Cache 1.26
   │
   ▼
Extraction
   │
   ▼
Semantic Content / Chunks
   │
   ▼
Knowledge 1.25
   │
   ├── Annotation
   ├── Derived Knowledge
   ├── Processing Runs
   ├── Dependency DAG
   └── Resolutor / Equalix
   │
   ├──────────────► Search Projections 1.31
   │
   ├──────────────► AI Runtime 1.30
   │
   └──────────────► Analytics
                         │
                         ▼
                 Facts / Aggregates / Metrics
```

Eventing 1.27 связывает изменения состояния и рабочие процессы на всём конвейере.

Identity 1.29 предоставляет доверенный контекст субъекта и арендатора.

Security 1.23 действует на всём протяжении конвейера.

Platform API 1.32 предоставляет стабильные внешние возможности.

Design 1.33 определяет будущую оболочку жизненного цикла Kubernetes.

## 6. Место событий и рабочих процессов

Design 1.27 намеренно является связующей основой выполнения.

```text
Events       = durable facts
Commands     = requests for work
Workflows    = stateful coordination
Processing Run = record of processing
Provenance   = explanation of derived state
Equalix      = controlled recalculation execution
```

Это не позволяет 1.28–1.31 вводить независимую семантику асинхронной обработки.

Это был главный вывод межплоскостного архитектурного обзора (2026-09-06, зафиксирован в [решении по результатам архитектурного обзора](../../docs/architecture/proposals/synanton-architecture-review-resolution.md)): Eventing нужно было задать как общую основу *до* того, как Ingestion (1.28), Identity (1.29), AI Runtime (1.30) и Search (1.31) можно было считать определёнными, поскольку каждая из этих плоскостей зависит от общих семантик доставки, повторов, идемпотентности и порядка, заданных только в 1.27. Их номера версий (1.28–1.31) отражают порядок авторства, а не порядок зависимостей; архитектурно 1.27 стоит перед всеми четырьмя. Design [1.27](../../docs/architecture/synanton-design-1.27.md) приведён в соответствие с этим принципом, а Designs 1.28, 1.29, 1.30 и 1.31 ссылаются на 1.27 как на используемую ими основу асинхронной обработки, вместо того чтобы определять собственную.

## 7. Идентификация и безопасность

```text
Identity 1.29
    │
    ▼
trusted principal
    │
    ▼
tenant membership / delegation
    │
    ▼
Security 1.23 authorization
    │
    ▼
resource / representation eligibility
```

Та же цепочка субъекта передаётся в асинхронные операции, выполнения ИИ, приём данных и административные операции.

Design 1.29 — семантический владелец субъекта, членства в арендаторе, федерации и делегирования. Design 1.32 владеет публичной **поверхностью API** управления идентификацией, построенной на этой модели: это не дубликаты, поскольку 1.29 определяет, *что такое* субъект, арендатор и делегирование, а 1.32 — как вызывающая сторона управляет ими по сети.

## 8. Граница среды выполнения ИИ

```text
Platform 1.30
  WHAT / WHY / SECURITY / PROVENANCE
              │
              ▼
Runtime implementation
  HOW / SCHEDULING / HARDWARE
              │
              ▼
GPU / CPU / remote inference
```

Первоначальная реализация GPU Runtime — отдельный проект и должна соответствовать контракту, которым владеет платформа. Design [1.20](../../docs/architecture/archive/synanton-design-1.20.md) (архивированный документ о плоскости выполнения GPU, включённый в базовую версию Design 1.22 согласно `docs/architecture/INDEX.md`) описывает предшествующую модель физической изоляции, которую формализует эта граница: 1.20 установил, что инфраструктура GPU физически изолирована от основной платформы; 1.30 добавляет поверх этой изоляции контракт выполнения моделей (реестр, версии, происхождение, оценка), не включая механизмы планирования среды выполнения в доменную модель платформы.

## 9. Граница поиска

Поиск использует канонические знания и формирует производные результаты поиска.

```text
Knowledge
   ├── lexical projection
   ├── vector projection
   └── graph projection
             │
             ▼
        Search 1.31
             │
      security-aware
      candidate generation
             │
             ▼
          ranking
```

Ни одна поисковая система не становится авторитетным источником. Фильтрация по безопасности выполняется при формировании кандидатов — до ранжирования, а не после ранжирования результатов. Те же правила допустимости применяются к побочным каналам метаданных (подсчётам фасетов, автодополнению, выделению фрагментов), чтобы через них нельзя было раскрыть существование или содержимое данных, к которым у запрашивающей стороны нет доступа.

## 10. Граница временного версионирования

Design [1.34](../../docs/architecture/synanton-design-1.34.md) добавляет межплоскостную временную семантику — поиск на заданный момент, серии версий, а также обработку исправлений и жизненного цикла — не вводя конкурирующую модель владения. Ответственность передаётся тем же плоскостям, которые уже владеют соответствующим состоянием:

```text
Ingestion 1.28
  owns VersionSeries / SourceVersion, published_at / observed_at / valid_from / valid_to,
  source lifecycle state, and authoritative source-version history
              │
              ▼
Knowledge 1.25
  owns derived knowledge; knowledge remains derived from a specific source version
              │
              ▼
Search 1.31
  owns temporal retrieval behavior; temporal eligibility joins security eligibility
  as a pre-ranking candidate constraint — never a post-ranking filter
```

Три временных измерения различаются и никогда не сводятся к одной временной отметке: `published_at` (когда источник объявил версию), `observed_at` (когда Synanton узнал о ней) и `valid_from`/`valid_to` (период её применимости). `current` означает **множество** временно допустимых версий, а не один глобально последний документ; тот же принцип «единственного глобального ответа нет» Design 1.31 применяет к ранжированию поиска (§9), а Design 1.25 — к производным знаниям.

Исправление версии источника классифицируется до запуска последующей обработки: исправление только метаданных (например, корректировка `valid_from`) обновляет затронутую поисковую проекцию на месте; исправление содержимого запускает полный путь пересчёта Resolutor/Equalix, установленный Design 1.25. Так временные исправления не вызывают ненужный пересчёт, а пересчёт остаётся единственным механизмом исправления производных знаний.

Режим юридической блокировки хранения (legal hold) и политика хранения остаются послойными и принадлежат соответствующим плоскостям (метаданные SourceVersion → Content Cache 1.26 → производные знания 1.25 → поисковые проекции). Design 1.34 не вводит единого владельца политики хранения для всей платформы.

## 11. Platform API

Внешний контракт ориентирован на ресурсы и версионируется.

Начальные ресурсы:

```text
tenants
principals
sources
source versions
ingestion runs
artifacts/content
knowledge/chunks/annotations
search
AI executions
workflows
operations
exports
```

Контракты OpenAPI/protobuf и CI проверки совместимости являются частью базовых требований к реализации.

Публичный ресурс `Operation` (принятие длительной работы и её состояние) — внешний контракт асинхронной работы. Он отличается от внутренней модели событий, команд и рабочих процессов Design 1.27 и не дублирует её. Один `Operation`, видимый клиенту, может опираться на сколь угодно сложный внутренний рабочий процесс, не превращая эту сложность в часть публичного контракта.

## 12. Жизненный цикл Kubernetes

Kubernetes — необязательная среда развёртывания.

Планируются следующие проекты управления жизненным циклом:

```text
synanton-platform-operator
content-extractor-operator
gpu-runtime-operator
```

Все операторы — проекты на Go.

Монолитный оператор не требуется.

До начала реализации каждый сервис должен пройти проверку совместимости с Kubernetes по Design 1.33.

CRD относятся только к управлению жизненным циклом и плоскости управления; типы объектов Kubernetes не входят ни в один доменный контракт или контракт бизнес-логики. Каноническое имя оператора — `content-extractor-operator`; оператор `content_retrieval` не вводится ни в одном документе серии.

## 13. Совместимость и соответствие контрактам

Базовая реализация 1.0 требует:

- контрактных тестов;
- негативных тестов безопасности;
- тестов идемпотентности и повторов;
- совместимости схем событий;
- CI для совместимости API;
- тестов жизненного цикла приёма данных и источников;
- проверки соответствия Content Cache;
- бенчмарка и оценки поиска;
- проверки соответствия среды выполнения ИИ;
- проверки совместимости операторов;
- тестов временного поиска и исправлений (точность версий, полнота временного поиска, доля временного загрязнения — см. Design 1.34 §38).

Дополнительные возможности, заявленные любой плоскостью (например, флаги возможностей бэкендов хранения в Content Cache 1.26), ДОЛЖНЫ быть подтверждены набором тестов соответствия этой плоскости до включения в промышленной среде: заявление о возможности без подтверждающих тестов не является поддерживаемой возможностью.

## 14. Последовательность реализации

Архитектура рекомендует следующий порядок:

1. **Завершить 1.32** и зафиксировать общие контракты API, ресурсов, ошибок и Operation. — *Выполнено 2026-10-17 (#246).*
2. **Зафиксировать 1.27** как общий асинхронный контракт. — *Выполнено 2026-10-17 (#247); реализация не начата.*
3. Реализовать первый вертикальный срез:
   `Ingestion → Content Cache → Eventing → Knowledge → Search`.
4. Добавить обеспечение требований Identity и безопасности на всём срезе.
5. Добавить контракт AI Runtime и проверку соответствия GPU Runtime.
6. Добавить аналитику как асинхронного потребителя производных данных.
7. Выполнить проверку совместимости с Kubernetes.
8. Реализовать независимые операторы на Go после проверки контрактов.
9. Провести межплоскостные тесты интеграции, отказов, восстановления и безопасности.

Шаги 1–2 указаны первыми, потому что от этих двух контрактов зависят все остальные плоскости (внешний контракт и внутренний асинхронный контракт соответственно); та же логика зависимостей ставит 1.27 перед 1.28–1.31 в §6.

Архитектура Platform 1.0 завершена, когда:

- [x] 1.22 остаётся базовой архитектурой.
- [x] 1.23 явно обозначен нормативным.
- [x] Консолидация 1.24 в 1.25 явно указана.
- [x] Для 1.26–1.33 согласованы междокументные ссылки и границы ответственности.
- [x] 1.27 задаёт общую семантику событий и рабочих процессов.
- [x] 1.28 определяет идентичность и версионирование источников, а также удаление.
- [x] 1.29 определяет канонических субъектов и цепочки субъектов.
- [x] 1.30 определяет семантику выполнения ИИ, принадлежащую платформе.
- [x] 1.31 определяет производный поиск и извлечение.
- [x] 1.32 определяет стабильный внешний API и API управления идентификацией.
- [x] 1.33 определяет готовность к Kubernetes без проникновения Kubernetes в доменную модель.
- [x] 1.34 определяет межплоскостное временное версионирование и поиск на заданный момент без конкурирующей модели владения.

Первые двенадцать критериев относятся к архитектуре и выполнены этим документом и принятыми Designs 1.22–1.34. Остальные четыре относятся к реализации и остаются открытыми — см. §15; это дальнейшая работа по реализации, а не препятствие для принятия архитектуры.

## 17. Итоговый тезис

Synanton Platform 1.0 — не набор независимых сервисов.

Это набор явных архитектурных контрактов с чёткими границами ответственности:

> **Ingestion устанавливает истину об источниках. Knowledge формирует производный смысл. Identity устанавливает, кто действует. Security определяет, что можно раскрыть. Eventing координирует изменения. AI Runtime выполняет вычисления. Search делает знания доступными для поиска. Analytics измеряет производное состояние. Временное версионирование устанавливает, когда оно было истинным. Platform API предоставляет стабильные возможности. Kubernetes управляет жизненным циклом инфраструктуры, не становясь частью доменной модели.**

Таким образом, архитектура остаётся:

**ориентированной на безопасность, учитывающей происхождение данных, управляемой событиями, допускающей пересчёт, независимой от хранилища, среды выполнения, поискового бэкенда и способа развёртывания, с временной семантикой и стабильным API.**
